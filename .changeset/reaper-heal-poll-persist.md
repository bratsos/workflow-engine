Two liveness fixes.

- `run.reapStuck` no longer fails a run it has just healed. A `PENDING` stage with no queued job is re-enqueued after the commit, and that post-commit touched neither the run nor a stage row, so the next sweep before any worker dequeued the job still found the run stuck, saw the recovered `PENDING` job as nothing missing and reaped the run with `STUCK_RUN_REAPED`. The heal refreshed the run's activity (`version` and `updatedAt`) only for a job transport that binds its reads to the transaction, which is the Prisma SQLite queue alone: the in-memory queue and the Prisma Postgres queue were exposed, and a second sweep (a sweep on another host, or one queued behind the first) reaped the healed run deterministically, not only under load. The heal now refreshes it on every transport, so the next sweep leaves the run alone and a sweep that read the run before the heal committed loses on `StaleVersionError`. `run.reapStuck` gains one `UPDATE` of the run row on the heal path of the in-memory and Postgres adapters; its other paths are unchanged. As on SQLite already, a refresh that loses to another writer, or a post-commit enqueue that fails, leaves the stage without a job until the sweep one threshold later.
- `stage.pollSuspended` no longer fails the stage and the run on the first store or blob error while the engine persists a legacy `checkCompletion` answer (the not-ready commit, the output blob write, the ready commit). Those errors were caught together with a throw from `checkCompletion` itself and went through the same failure path. They are now retried as a durable replay that throws is: with the attempts the stage's job has left, the stage `SUSPENDED`, `attempt` bumped, the error on `errorMessage`, `stage:retrying` emitted and the claim written back on a `2^attempt` second backoff. Once the attempts are spent, or the error is deterministic, the stage and the run fail with the store's error, as before. A poll that persists its answer ends the streak, so only consecutive failures count, and a store that also fails the retry write rejects the dispatch. A throwing `checkCompletion` is unchanged: it fails the stage and the run on that poll; only the message for an answer of `null` or `undefined` changes (`checkCompletion returned null`). The statements of `job.execute` and of the success paths of `stage.pollSuspended` are unchanged; a poll whose persistence fails now issues the retry's statements (a read of the stage's job rows, then one transaction updating the stage and appending `stage:retrying`) instead of the failure's.

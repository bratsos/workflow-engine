Two liveness fixes.

- `run.reapStuck` no longer fails a run it has just healed. A `PENDING` stage with no queued job is re-enqueued after the commit, and that post-commit touched neither the run nor a stage row, so the next sweep before any worker dequeued the job still found the run stuck, saw the recovered `PENDING` job as nothing missing and reaped the run with `STUCK_RUN_REAPED`. The heal refreshed the run's activity (`version` and `updatedAt`) only for a job transport that binds its reads to the transaction, which is the Prisma SQLite queue alone: the in-memory queue and the Prisma Postgres queue were exposed, and a second sweep (a sweep on another host, or one queued behind the first) reaped the healed run deterministically, not only under load. The heal now refreshes it on every transport, so the next sweep leaves the run alone and a sweep that read the run before the heal committed loses on `StaleVersionError`. `run.reapStuck` gains one `UPDATE` of the run row on the heal path of the in-memory and Postgres adapters; nothing else changes, and `job.execute` and `stage.pollSuspended` issue the same statements as before.
- `stage.pollSuspended` no longer fails the stage and the run when the engine's own write of a legacy `checkCompletion` answer fails (the not-ready commit, the output blob write, the ready commit). Those errors were caught together with a throw from `checkCompletion` itself and went through the same failure path, so one transient store or blob error ended the run with nothing to retry it. The stage now stays `SUSPENDED`, its claim handed back on a 2 second backoff with a warning log, and the next poll asks `checkCompletion` again, as a durable replay that throws is retried. A throwing `checkCompletion` is unchanged: it fails the stage and the run on that poll.

Durable steps, injected AI services, one AI primitive with a realtime/batch policy, a builder-first typed workflow API, and the 1.0 removals.

**Breaking (major):**

- Removed the APIs deprecated for 1.0: `ModelStatsTracker`, `getModelById`, `ModelWithRecorder`, `printAvailableModels`, `getRegisteredModel`, `listRegisteredModels`, `getDefaultModel`, `modelSupportsBatch`, the positional `recordCall(modelKey, prompt, response, tokens, options)` overload (the object form stays), `requireStageOutput`, and `apiKey` on the suspended state schema. Check batch capability with `getModel(key).supportsAsyncBatch`; configure models with `registerModels()`.
- `defineWorkflow` no longer takes an `output` option. The workflow output schema is always the last stage's output schema (or the merged object of the last parallel group).
- `StageContext` and `CheckCompletionContext` gained `step`, `ai` and `aiLogger`, all **required** — `StageContext.step` is no longer optional, and `CheckCompletionContext` now carries a `step` scoped to the same stage record. Hand-built contexts (custom hosts, tests that construct a context by hand) must provide them; `createStepApi()` from `@bratsos/workflow-engine/kernel` builds a ledger-less step API that throws `StepLedgerNotConfiguredError`.
- `ctx.log` and `ctx.onLog` are typed as returning `void`. Code that awaited them still compiles; the type no longer suggests it.
- `AIStreamResult.rawResult` is `undefined` when the stream came from an adapter.
- `ModelKey` is open in both forms. The *type* accepts any string, and the exported *zod schema* is now `z.string().min(1)` instead of a registry refinement — a `schemas.config` field typed with it no longer rejects an unregistered key at `run.create` with "Model not found". Validation stays at `getModel()`.
- `WorkflowBuilder.stage(prebuilt)` and `.pipe(prebuilt)` now check the stage's declared context against the accumulated one. A stage that requires a key no earlier stage produces (or produces with an incompatible type) no longer compiles; the parameter resolves to `{ __error: "stage requires context keys not produced by earlier stages: ..." }`. Stages built without an explicit context are unaffected.
- The Prisma schema gains a `WorkflowStep` model (`attempt`, `leaseExpiresAt`, `deadlineAt` included) used by `PrismaStepLedger`; consumers using durable steps need a migration.

**New features:**

- **Durable steps.** `ctx.step.run(id, fn, { leaseMs, retries, retryDelayMs })` (`retryDelayMs` takes a duration string too), `ctx.step.waitFor(id, { poll, ready, every, timeout, pollBackoffMs })`, `ctx.step.waitForSignal(id, { timeout })` and `ctx.step.sleep(id, duration)` record side effects in a `StepLedger` (`InMemoryStepLedger`, `PrismaStepLedger`); a suspended stage resumes by replaying `execute()` with completed steps answered from the ledger. A `step.signal` kernel command completes a signal wait and is idempotent. Leases re-claim steps left `running` by a dead worker, `retries` re-run a thrown step, wait deadlines are stored once and never slide (`StepTimeoutError` on expiry), a throwing `poll` backs off instead of failing the stage, replay saves artifacts, and re-running a stage from scratch clears its ledger rows. Control-flow errors are branded (`isStepControlFlowError`) and a stage body that swallows one still suspends.
- **`ctx.step.ai`.** `generateText` and `generateObject` are memoized through the ledger. `map(id, items, spec)` runs one prompt per item under `policy: "auto" | "realtime" | "batch"` with the same schema validation and repair on both paths, an in-process concurrency limit, a call budget (`AiMapBudgetExceededError`), a stored batch deadline, and `onExpiry: "fail" | "partial"` (`AiMapBatchFailedError`). All batch bookkeeping lives in step results.
- **`ctx.ai` and `ctx.aiLogger`.** `createKernel({ services: { aiLogger, ai? } })` provides a lazily built `AIHelper` on every stage and `checkCompletion` context under the topic `workflow.<runId>.stage.<stageId>`, with call logs in the run's log table. `createMockAIHelperFactory()` in `@bratsos/workflow-engine/testing` provides the mock for tests. Accessing `ctx.ai` without services throws `AIServicesNotConfiguredError`.
- **Adapter seam.** `AIHelperOptions.adapter: AIAdapter` swaps the transport for any subset of `generateText`, `generateObject`, `embed` and `streamText` below logging and cost; child helpers inherit it. Adapter responses may carry `costUsd`, recorded as the reported cost.
- **Timeouts.** `AIHelperOptions.timeout.perCallMs` and per-call `timeoutMs` on text, object, embed and stream options; expiry throws `AICallTimeoutError` and still logs the failure row.
- **Builder-first workflows.** `defineWorkflow(id, { input }).stage(id, definition)` infers the context from earlier stages so `ctx.require()` is typed and `dependencies` only accepts earlier ids; `.stage(prebuilt)`, `.pipe()`, `.parallel([...])` and `.parallel((group) => ...)` carry the same inference; `InferWorkflowContext`, `InferWorkflowInput`, `InferWorkflowOutput`, `InferWorkflowStageIds` and `InferStageOutputById` expose the inferred types.
- The package now ships `prisma/schema.prisma`, and the Prisma adapters no longer import `@prisma/client` (Prisma 7's generator has no fixed client path).
- **Durable steps under `Promise.all`.** When one of several concurrent steps suspends, the stage factory now lets every in-flight `run` finish and record — bounded by the longest remaining lease — before the suspension is persisted, so the replay finds completed rows instead of meeting `StepInFlight` until the leases expire.
- **Step options on single AI calls.** `ctx.step.ai.generateText(id, model, prompt, options?, stepOptions?)` and `generateObject(..., schema, options?, stepOptions?)` forward a `StepRunOptions` (`retries`, `retryDelayMs`, `leaseMs`) to the underlying `step.run`, so one model call retries durably like any other step.
- **`ctx.step.ai.streamText(id, model, prompt, options?, stepOptions?)`.** Streams through `ctx.ai.streamText` on the first execution (forwarding `onChunk`) and stores the final text, tokens, cost and reasoning as one `run` step; a replay returns the stored `StepStreamResult` without contacting the model and calls `onChunk` once with the whole text. For hosts that kill an idle non-streaming connection.
- **`ctx.step.ai.map` additions.** A failed item carries `errorName` (the `Error.name` of the last failure, memoized so it survives replays; never a `cause` — results must stay JSON). `realtime.minDelayMs` paces each concurrency slot, replacing hand-written cooldowns. `stream: true` sends realtime items through `ctx.ai.streamText`, with `schema` still validating the collected text.
- **Test harness.** `createTestHarness({ workflows, services?, clock?, stepLedger?, ... })` in `@bratsos/workflow-engine/testing` returns the kernel, every in-memory port, the step ledger, the AI logger, the mock AI factory and the fake clock, plus `run(workflowId, input, config?)` (drives claim → execute → poll suspended → flush → advance until the run is terminal) and `tick()` (one round, returning a `TickReport`). `createTestKernel` is exported from the same entry.
- **Mock AI scripting.** `createMockAIHelperFactory({ helper })` hands out the caller's instance, and `createAtTopic`/`createChild` construct through `this.constructor`, so a `MockAIHelper` subclass survives. `failOnce(match, error?)` arms a one-shot failure (substring, RegExp, or a predicate over `{ modelKey, prompt, kind }`), and `mockObjectResponseForSchema(schema, value)` dispatches object responses on Zod schema identity.
- **Host helper ergonomics.** Every field of `RunMaintenanceTickOptions` and `ExecuteJobWithHeartbeatOptions` is optional, with `HOST_DEFAULTS` (which now also carries `workerId` and `logPrefix`) applied inside. `runMaintenanceTick(kernel)` and `executeJobWithHeartbeat(kernel, { jobTransport, job })` work as-is.
- **Export surface.** `WorkflowRegistry` is exported from the root entry alongside `Workflow`, and `TextInput`, `ContentPart`, `TextPart`, `MediaPart` and `StreamTextInput` are exported from both the root and `/client`, so every type in a public method signature is importable.
- Reference `skills/workflow-engine/references/12-durable-steps.md` documents all of the above and the migration from `defineAsyncBatchStage` to steps. `skills/workflow-engine/migrations/migrate-0.13-to-1.0.md` is the upgrade guide: a column-level database checklist with SQL (the `workflow_steps` table, `ai_calls.batchId`/`requestId`, and the columns every dispatch writes), the API removals with replacements, the builder and `defineAsyncBatchStage` → `ctx.step.ai.map` migrations, `createKernel({ services, stepLedger })`, the AI SDK 7 peer ranges and the behaviour changes.

**Fixes from the first real-world runs of 1.0.0-alpha.0:**

- `AIAdapter.generateObject` results were read from `output` instead of `object`, so every adapter-based `generateObject` (and every `ctx.step.ai.map` item with a schema) returned `undefined`, logged an empty response and crashed. The object is resolved once from the adapter response; `generateText` reads the adapter's structured `object` the same way. The adapter seam is now covered end to end through the kernel (a real `createAIHelper` over a fake adapter across `generateText`, `generateObject`, `streamText`, `map` realtime and `map` with repair).
- `ctx.step.ai.map` repair now engages for any error that carries the model's raw text (`text` or `cause.text`), a `ZodError` or a JSON `SyntaxError`, not only the AI SDK's `AI_NoObjectGeneratedError`; `NoObjectGeneratedError` is re-exported from the root entry so adapters can throw it. Realtime item retries (`realtime.retries`) run **in-process** — wait `retryDelayMs`, bump the ledger row's `attempt`, call again — instead of suspending and replaying the whole stage. `ctx.step.run` retries still suspend the stage.
- The step seq ordinal is stable across replays of a stage that runs a map: item seqs are reserved in item order before any ledger lookup resolves, so a slow ledger cannot permute them and a `step.run` after the map is no longer reported as "non-deterministic step order".
- `NodeHost.stop()` waits (bounded by `shutdownTimeoutMs`, default 10s) for the job in flight and then runs a final `outbox.flush`, so `workflow:completed` for a run finished by that process is published before it exits instead of by whichever process ticks next; `flushOutboxOnStop: false` opts out. The serverless host, which has no lifecycle, flushes after each `handleJob` (`flushOutboxAfterJob`, default true, bounded by `outboxFlushTimeoutMs`). The remote package is an activity worker with no outbox and is unchanged.
- A stage failure with job attempts left is no longer recorded as `FAILED`: `job.execute` takes the job's `attempt`/`maxAttempts` (both hosts and the test harness pass them), leaves the stage `PENDING` with the error on `errorMessage`, keeps its ledger rows, and returns `willRetry: true`; the host re-enqueues through `jobTransport.fail(jobId, error, true)`, whose contract now states the transport must re-queue with backoff. With no attempts left the stage is `FAILED` and `run.transition` runs immediately on every host — previously a serverless consumer whose transport acknowledged without re-enqueueing saw a `FAILED` stage under a `RUNNING` run until `run.reapStuck`. The `maxRetries` field of the config presets is not read by the kernel; the transport's `maxAttempts` is the retry budget.
- Google batch structured outputs send the full JSON Schema again. `@ai-sdk/google` (checked through 4.0.63) can only express a response schema as Gemini's OpenAPI-style `responseSchema`, which flattens nested discriminated unions, so on 1.0.0-alpha.0 every item of such a batch failed validation and was re-run realtime by repair (2x calls, discount lost). The engine now substitutes `generationConfig.responseJsonSchema` — what 0.13 sent through `@google/genai` — into the inline batch body per request key at the `fetch` boundary (`resolveAiSdkBatchModel` accepts `apiKey`/`baseURL`/`fetch` from `BatchOptions` for every vendor now). A batch too large to inline is uploaded as a file and keeps the provider's schema, with a WARN. The realtime `generateObject` path used `Output.object` in 0.13 as well and is unchanged. `getResults` logs a WARN naming the batch id and the first issue when more than half of a batch fails schema validation, and batch accounting rows now store the item prompt and `metadata.durationMs` (the batch wall time) like realtime rows.

**Fixes from the second consumer trial:**

- The stage wrapper no longer dereferences `ctx.step` when a hand-built context (custom host, a unit test calling `stage.execute(ctx)` directly) has none; the type stays required, every runtime probe is optional-chained.
- `createPrismaWorkflowPersistence(prisma, { statusEnumName })` names the Prisma enum the Postgres claim statement casts with (default `"Status"`; the cast dates from 0.11). The statement is issued through `$queryRawUnsafe` with positional parameters when the client has it; `$queryRaw` stays the fallback for the default name. Both the persistence and `createPrismaJobQueue` take a `now` clock and bind that JS `Date` instead of `NOW()`, so raw-SQL timestamps are UTC like every Prisma write and follow an injected clock; `claimNextPendingRun({ now })` receives the kernel clock.
- Batch provider resolution: the call's `batch.provider` first, then the model's new registry field `batchProvider` (`"openrouter" | "google" | "anthropic" | "openai"`), then the slug's native vendor, then OpenRouter. A model that names `batchProvider: "openrouter"` is batched there even without a catalog `:batch` row. When the vendor SDK is not installed (`@ai-sdk/anthropic` / `@ai-sdk/openai` are optional peers) and OpenRouter can batch the model, the helper falls back to the OpenRouter transport with a WARN instead of failing the submit with `Package "@ai-sdk/anthropic" is required`. Sync-generated entries (all `provider: "openrouter"`) keep resolving to their native vendor by default, as before. The OpenRouter batch client was verified live: the documented body shape is what the engine sends; a creation error `does not have a :batch endpoint` (the catalog row exists but the endpoint is not live for that model) is now explained in the error.
- `MockTextResponse.output` seeds structured output for `generateText` + `Output.object(...)`; when omitted, the scripted `text` is parsed and validated through the output spec exactly as the AI SDK does (rejecting with `NoObjectGeneratedError`). The mock's `streamText` is unchanged: the real `streamText` has no `output` option.
- `WorkflowRun.totalCost` / `totalTokens` are written on completion from `services.aiLogger.getStats("workflow.<runId>")` (falling back to the stages' `metrics` sum without services), and carried on `workflow:completed`. The 04-ai-integration paragraph now describes what the kernel does.
- A completed job retry clears the stage's stale `errorMessage` (`UpdateStageInput.errorMessage` accepts `null`). `WorkflowStage.attempt` keeps counting `run.rerunFrom` reruns; job retries are counted on the `job_queue` row, which the reference now states.
- A job retry of a thrown stage keeps its ledger rows and replays them (a consequence of recording retryable failures as `PENDING`): a map of N items followed by a throw costs no extra model calls on the retry. Only `run.rerunFrom`, or executing a stage whose attempts were exhausted, clears the ledger.
- `createPrismaStepLedger` is exported from the root entry (a test now pins it, alongside the other `createPrisma*` helpers and `NoObjectGeneratedError`).
- `generateObject` and `generateText` + `Output.object` now send identical requests: the one difference was the default temperature (`0` for `generateObject`, `0.7` for `generateText`). Neither sends a default any more — see the fourth-round entry below. This was the difference behind the consumer's "generateObject is less reliable than generateText + Output.object on the same model" — same messages, same JSON response format, different sampling.
- The persistence reference lists every delegate `EnginePrismaClient` requires and states that a wall of `PrismaClient is not assignable to EnginePrismaClient` errors means one of them is missing (after 1.0, almost always `workflowStep`).

**Fixes from the third consumer trial (kernel inside one Prisma transaction per tick):**

- `PrismaStepLedger.claim` and `acquireIdempotencyKey` no longer rely on a caught unique violation on Postgres — a failed statement aborts a consumer's enclosing transaction (`25P02`) on every replay that re-claims completed steps. Both insert through `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`) and read the row back; "existing records win conflicts without throwing" now holds inside a transaction. `createPrismaStepLedger(prisma, { databaseType: "sqlite" })` keeps the create-and-catch path where `skipDuplicates` does not exist.
- `createPrismaBlobStore(prisma)` / `PrismaBlobStore`, backed by an optional `WorkflowBlob` model (`workflow_blobs`, in `prisma/schema.prisma`), so a Prisma deployment has a blob store shared by every process without object storage; it requires only the `workflowBlob` delegate (`BlobPrismaClient`), not a change to `EnginePrismaClient`. A replay whose blob store lacks a completed stage's output now fails naming the blob key and the shared-store requirement instead of "missing the output of execution group N". The reference documents that the blob store must be shared by every process that executes or polls a run.
- Raw SQL timestamps: `claimNextPendingRun` and the Postgres `dequeue` bind a JS `Date` from the configured clock (`now` option; the kernel passes its clock to the claim) instead of `NOW()`, which wrote session-local time into naive `TIMESTAMP(3)` columns while Prisma wrote UTC.
- `ctx.step.waitFor` narrows through a type-guard `ready` (`(v): v is Done => ...` returns `Done`); the boolean form is unchanged.
- Replays no longer re-emit `stage:suspended` / `workflow:suspended` on every poll while the stage is still waiting on the same step with the same deadline; the events are emitted when the wait starts and when the stage moves to a different wait (a run polled every ~8s for 5 minutes emitted 73 pairs on alpha.0).
- Hosts treat a job whose run, workflow or stage no longer exists as a dead job: `executeJobWithHeartbeat` logs it, fails and acknowledges it, and returns `{ outcome: "failed", dead: true }` instead of throwing — an orphan `job_queue` row no longer aborts a serverless tick (or a transaction-per-tick consumer's whole tick).
- OpenRouter's "No endpoints found that can handle the requested parameters" is wrapped with what to change: it is the outcome of the default `routing.requireParameters: true` excluding endpoints that ignore a requested parameter (typically `maxTokens`); the error names `routing: { requireParameters: false }`. The default stays `true` (chosen in 0.13 so a request's parameters are honoured rather than silently dropped).
- Reference fix: `eventSink` is `{ emit }`, not `{ publish }`.
- The one "OpenRouter API key is missing" on a replayed retry could not be reproduced: the realtime path uses the provider package's default `openrouter` instance, which reads `OPENROUTER_API_KEY` from `process.env` at call time (no caching in the engine), and the stage AI helper is built the same way on the job and poll paths; the only engine-side explanation is the variable being absent from that process's environment at that moment. Inject the key explicitly through a `providerResolver` in `services.ai` to remove the dependency on process environment.
- `@bratsos/workflow-engine/testing` imports nothing from vitest, so it loads from a plain `tsx` script. The conformance suites take the test primitives as a third argument: `persistenceConformanceSuite(name, factory, { describe, it, expect, beforeEach })` (same for `aiCallLoggerConformanceSuite` and `jobQueueConformanceSuite`); `ConformanceTestApi` is exported. `check:bundle` now guards `dist/testing/index.js` against vitest (and the other forbidden peers) like it guards `client.js`.
- The surfaces marked "removal at 1.0" are gone: `KernelConfig.scheduler` and `NoopScheduler`, `RunCreateCommand.metadata` (use `annotations`), the `ArtifactPersistence` methods and the eight legacy query methods on the `WorkflowPersistence` port, `enqueue` on the `JobQueue`/`JobTransport` ports (`enqueueParallel([job])`), and the `defineAsyncBatchStage` export from the root and `/client` entries (the async-batch mode itself still runs; `defineStage({ mode: "async-batch", checkCompletion })` is the internal equivalent). The built-in adapters keep the removed methods as plain class methods. `SuspendedStateSchema.submittedAt/pollInterval/maxWaitTime` stay, with a corrected note: `defineStage()` back-fills them for async-batch `checkCompletion`, so they go away with that mode, not on their own. `workflow-engine-codemod --from 0.13` (new) and `--from 0.11/0.12` flag `defineAsyncBatchStage`, `checkCompletion`, `requireStageOutput`, `experimental_output` and the removed model helpers with the guide pointer (rule 7).

**Fixes from the benchmark round (1.0.0-alpha.8) — two long-standing defects, both present in 0.13.0 as well:**

- **`run.claimPending` enqueued the first-stage job inside the claim transaction, so a fast job loop wedged the run it had just claimed.** The job transport is a separate connection that takes no part in that transaction, so the job row was visible while the run it named was still `PENDING` everywhere else. A worker whose job loop polled faster than the claim committed dequeued it, `job.execute`'s ghost guard discarded it as an orphan, and nothing re-enqueued it: the run sat `RUNNING` with no job until `run.reapStuck` reaped it minutes later. Measured on this worktree with a 2 ms job poll: **62 of 100 freshly created runs wedged; 0 of 100 after the fix** (0 of 200 at a 1 ms poll). Invisible at the 1000 ms default and worse the shorter the poll, which is exactly what a caller chasing near-synchronous behaviour reaches for. Two changes, either sufficient on its own: `run.claimPending` now defers the enqueue to the kernel's post-commit step, like `run.transition` and `run.rerunFrom` already did (the run is committed `RUNNING` before its job exists; `claimed[].jobIds` still carries the ids, and every claimed run's enqueue is attempted even if another's fails); and a job whose run is still `PENDING` is reported as a race rather than an orphan — `JobExecuteResult.ghostReason` is `"race"` or `"orphan"` alongside `ghost: true`, and both hosts re-deliver a `"race"` (through `fail(jobId, error, true)`, so the transport's usual backoff applies, while the job's attempt budget lasts) instead of throwing it away. A terminal run's job is still failed terminally, with no `run.transition`. `run.reapStuck`'s PENDING-stage-without-job sweep remains the backstop for a job lost after the commit, and the enqueue is idempotent on `(workflowRunId, stageId)`, so it cannot double-queue. **No migration.** A custom host that read `ghost` alone keeps working (it just keeps discarding racing jobs); read `ghostReason` to get the recovery.

**Fixes from the seventh consumer round (1.0.0-alpha.7, host-node 0.4.4) — `run.rerunFrom` wedged the run it was rerunning:**

- `run.rerunFrom` deleted the stage records at and after the target execution group but never touched their `job_queue` rows, then re-enqueued the same `(workflowRunId, stageId)` with an unconditional insert. On a schema declaring `@@unique([workflowRunId, stageId])` the insert failed with `P2002` — post-commit, so the run was left wedged as `RUNNING` with a fresh `PENDING` stage and only the stale terminal job row, and `run.reapStuck`'s PENDING-without-job sweep re-enqueued through the same path and threw on every tick, so the run could never self-heal. On a schema without the unique, every rerun instead accumulated another job row per stage. Three changes, each of which fixes it on its own: `run.rerunFrom` retires the job rows of every stage record it deletes through a new `JobTransport.deleteByRunAndStages(workflowRunId, stageIds)` (this is what covers the downstream stages a rerun deletes without recreating — nothing would ever enqueue over their rows); `enqueueParallel` (and the built-in adapters' legacy `enqueue`) is idempotent on `(workflowRunId, stageId)`, replacing any row already queued for a pair in the same transaction as the insert and resetting `attempt`, `status`, `workerId`, `lockedAt`, `lastError` and `nextPollAt`, which also makes the reaper's recovery sweep safe on any schema; and the reference `prisma/schema.prisma` declares `@@unique([workflowRunId, stageId])` on `JobQueue`, covered by `jobQueueConformanceSuite` so both adapters are checked. The old row is deleted rather than marked terminal: it is a row for an execution whose stage record has just been deleted, so there is no stage row left for it to be history of. Verified against Postgres with the constraint in place: a failed 3-stage run rerun twice in a row ends with exactly one job row per stage and the stages before the rerun target still at `attempt 0`.
- **Migration:** add `@@unique([workflowRunId, stageId])` to your `JobQueue` model. The index build fails while duplicate rows exist, and pre-upgrade reruns may have left some — collapse them first (keep the newest row per pair, with no worker mid-job) and then create the index; the 0.13 → 1.0 guide has the SQL. A deployment that cannot take the constraint yet still gets the fix, since the enqueue paths are idempotent either way; the constraint is what stops a custom `JobQueue` from writing a duplicate.
- **Custom `JobQueue` / `JobTransport` implementations:** `deleteByRunAndStages(workflowRunId, stageIds)` is a new required method, and `enqueueParallel` must be idempotent on `(workflowRunId, stageId)` as described above. Both are in the published conformance suite.
- `NodeHostConfig.workerId` reaches `job_queue.workerId`. The row is written by the job queue, which is constructed before the host and, given no `workerId` of its own, generated `worker-<pid>-<timestamp>` — an id matching no host, so a job row could not say which worker ran the stage unless the consumer remembered to pass the same id to `createPrismaJobQueue` as well. `createNodeHost(...).start()` now offers its `workerId` to the transport through an optional `JobTransport.adoptWorkerId(workerId): string`, implemented by `PrismaJobQueue` and `InMemoryJobQueue`: a queue built without an explicit `workerId` adopts the host's, a queue built with one keeps it and the host logs a single `workerId mismatch` line naming both ids. Drop the `workerId` argument from `createPrismaJobQueue(prisma)` under a host; keep it only where no host supplies one. The port method is optional, so a custom transport needs no change.
- `@bratsos/workflow-engine-host-node` 0.4.4: a multi-stage run is no longer pinned to the worker that completed its previous stage. That worker is the one that dispatches `run.transition`, so it enqueued the next execution group in-process and went straight back to `dequeue()` while every other worker was still parked in its `jobPollIntervalMs` timer — measured with four identical workers, four 4-stage runs each ran on exactly one worker. The job loop now pauses for a uniform draw over `[0, postJobYieldMs)` after a *completed* job (only that outcome enqueues a successor from this process), which gives the completing worker the same phase every competitor has. `NodeHostConfig.postJobYieldMs` defaults to `jobPollIntervalMs`; `0` disables the pause and restores the old behaviour. The tradeoff is latency on a run one worker keeps advancing, so the pause is skipped while the loop is draining a backlog — as soon as `dequeue()` returns a job from a different run than the one just completed, the worker stops pausing until the queue next comes back empty, so a backlog costs at most one pause rather than one per job. Correctness is unchanged either way (every stage always ran exactly once); this only decides which worker picks a stage up.

**Fixes from the sixth consumer round (1.0.0-alpha.6) — `z.record` under OpenAI strict outputs:**

- A `z.record()` reached OpenAI strict structured outputs (native and through OpenRouter, realtime and `:batch`) as `{ type: "object", propertyNames, additionalProperties: <schema> }` and every request was rejected with `'propertyNames' is not permitted` (strict mode permits neither keyword and has no map type). For the OpenAI target a record is now sent as an array of `{ key, value }` objects — an enum key constraint is kept on `key`; records nested in objects, arrays, tuples, union branches and `$defs` are covered; an optional record is nullable like any optional property — and the reply is rebuilt into the object before validation (last duplicate key wins), so the caller's Zod schema sees the original shape. `z.looseObject`/`.catchall()` objects are sent closed. Verified live on OpenRouter `openai/gpt-5-nano` through `generateObject`, `generateText` + `Output.object` and a one-item batch. The Google target is untouched (Gemini expresses records natively).
- The inverse transform — optional-property nulls removed, record pairs rebuilt — is one pass, `restorePortableValue(value, jsonSchema)`; `stripOptionalNulls` stays exported as an alias. It runs in the realtime middleware (`generateObject`, `generateText` + `Output.object`; a streamed JSON reply is now restored too, its text deltas buffered per text part and emitted at `text-end`) and on the OpenAI/OpenRouter batch `getResults` path.
- A schema keyword OpenAI strict mode cannot express and the engine has no rewrite for (`patternProperties`, `unevaluatedProperties`, `minProperties`, `maxProperties`, `unevaluatedItems`, `contains`, `minContains`, `maxContains`, `uniqueItems`, `not`, `if`/`then`/`else`, `dependentRequired`, `dependentSchemas`) now fails at the engine boundary with `UnportableSchemaError` (`path` as a JSON pointer, `keyword`, `target`; exported from the root entry) before any request is sent — a realtime call throws it, a batch submit fails with it — instead of a provider 400 per item.
- `StageContext.attempt`, reported `undefined` in a stage body: the public `StageContext` has never declared it, so nothing changed; the stage row's `attempt` (`WorkflowStage.attempt`, via `ctx.stageRecordId`) is the source of truth.

**Fixes from the fifth consumer round (1.0.0-alpha.5, host-node 0.4.3) — two orchestrating processes replayed the same suspended stage:**

- `stage.pollSuspended` claims a suspended stage before doing any work on it. Two processes with orchestration on (or two overlapping ticks in one process) both read the same stage from `getSuspendedStages` and both ran its body — a durable stage's `execute()` replayed three to five times after its batch settled, and the app's persist transaction ran as many times; the run-level claim guarded only the final write. The handler now issues a version-guarded `updateStage(id, { nextPollAt: now + lease, expectedVersion })` per stage, outside the per-stage transaction, before `checkCompletion`, a replay or the wait-deadline check; a `StaleVersionError` means another poller holds it and the stage is skipped. The lease is `max(pollInterval, 60s)`, bounded by `maxWaitUntil` while that deadline is ahead. Every outcome still writes `nextPollAt` explicitly (a re-suspend writes the step's `nextPollAt`, not-ready writes `now + pollInterval`, completed/failed/cancelled write `null`, a skipped claim outcome hands the stage back to the next tick), so the lease value only survives a process that dies mid-replay — that stage is picked up again once the lease elapses. The in-memory persistence behaves the same, so `createTestHarness` and a real deployment agree. No schema change: the claim uses the `version` column `updateStage` already guards on.
- A claim outcome that finds the run no longer `RUNNING` marks the stage `CANCELLED` only when the run is `CANCELLED`. A run that is `COMPLETED`, `FAILED` or gone was finished by another orchestrator (its lease elapsed while this one was still replaying); the stage row already carries that outcome and is left alone — two runs had ended with a `CANCELLED` stage under a `COMPLETED` run.
- `@bratsos/workflow-engine-host-node` 0.4.3: an orchestration interval firing while a tick is still in flight is skipped, not queued (a replay longer than `orchestrationIntervalMs` no longer overlaps the next tick in the same process), `orchestrationTicks` counts only ticks that ran, and `stop()` waits for the in-flight tick (bounded by `shutdownTimeoutMs`) before the final outbox flush. The serverless host is caller-driven and unchanged.

**Fixes from the fourth consumer round (1.0.0-alpha.3):**

- OpenAI strict structured outputs (native, and through OpenRouter — seen on `openai/gpt-5-nano`, realtime and batch) also require every property to be listed in `required`, so an optional property still failed with `required is required to be supplied and to be an array including every key in properties`. The OpenAI rewrite now lists every property of every object in `required` and sends an optional, non-nullable property as `anyOf: [<original>, { type: "null" }]`, as OpenAI documents; a reply's `null` for such a property is then removed before validation — recursively through nested objects, arrays and union members, `$defs` followed — so the caller's Zod schema (`.optional()`) still parses (`stripOptionalNulls` in `schema-portability.ts`). A `null` the original schema admits (required or `.nullable()`) is kept. The middleware applies it to `generateObject`, `generateText` + `Output.object` and every `ctx.step.ai.*` call; the OpenAI and OpenRouter batch bodies carry the same schema and `getResults` strips before validating. Google and other targets are untouched. Verified live through OpenRouter → `openai/gpt-5-nano` with a discriminated union whose members have optional properties.
- No default `temperature` is sent. GPT-5 endpoints reject `temperature: 0.7` under OpenRouter's `requireParameters`, and the alpha.1 unification (`generateObject` 0 → 0.7 to match `generateText`) had introduced a default no provider needs. `generateText`, `generateObject`, `streamText`, `ctx.step.ai.*`, `map` and both batch bodies carry `temperature` only when the caller sets it; the provider's own default applies otherwise. Set `temperature` explicitly where a fixed value was relied upon.
- `run.transition` no longer copies the run's max stage `attempt` onto the next execution group: after a retried stage 1 (attempt 2) a stage 2 that had never executed read `attempt 2`. A stage's `attempt` counts the executions of its own row — job retries and `run.rerunFrom` reruns — so a fresh downstream stage starts at 0 (the `prepareExecutionGroup` `"max"` mode is gone). Consequence for annotations: after a rerun, a recreated downstream stage's annotations carry attempt 0 again; only the rerun target's row is bumped.
- A `ctx.step.ai.map` batch item bound for the repair pass was listed in the `${id}:collect` summary under both `failed` (with its batch tokens and cost) and `repair` (with the same as its prior attempt), so its batch cost counted twice. Each item is now listed once: under `repair` when it will be re-prompted (the item's verdict then continues from that prior — batch cost plus the repair call), under `failed` only when the batch verdict is final (`repair.attempts: 0`).

**Fixes from the third consumer round (1.0.0-alpha.2):**

- `WorkflowStage.attempt` is persisted: `UpdateStageInput.attempt` exists and the Prisma adapter writes it, so a stage row counts its job retries (it stayed at 0 through three attempts while `version` advanced; the in-memory adapter already merged it).
- A retried stage that completes through a suspension — the batch poll/collect resume, a `waitFor`, a `checkCompletion` — clears its stale `errorMessage` like a direct completion does.
- Ledger rows keep their attempt history: a `run` step or map item re-opened for a new job attempt goes back to `running` with no lease and keeps its `attempt` (a row that read `failed attempt 3` re-runs as attempt 4) instead of being reset to 0; in-process map retries increment the row's attempt rather than assigning it.
- `outbox.flush` claims rows before it emits them: `WorkflowPersistence.claimUnpublishedOutboxEvents(limit)` stamps `publishedAt` atomically (`UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING` on Postgres, a per-row compare-and-set on SQLite and in memory) and `releaseOutboxEvents(ids)` hands back the events of a run whose emit threw. Two hosts flushing the same outbox — a cron tick and a request-kicked tick — no longer both deliver `workflow:created`. Both methods are required on a custom `WorkflowPersistence`; the conformance suite covers them.
- OpenRouter batch status/results schemas accept `null` for every field an upstream may null (`results[].response.request_id` came back `null` from deepseek via Together, and the poll looped on "invalid batch object" until the deadline).
- The first three consecutive failures of a `waitFor` poll are logged at DEBUG and the streak escalates to WARN from the fourth (OpenRouter answers 404 to the first status check after a submit); the count is stored on the row (`waitState.pollFailures`) and reset by a poll that returns.
- The missing-vendor-SDK fallback to OpenRouter no longer requires a catalog `batchModelId`: a batch-capable entry without one assumes the `<id>:batch` row (as the sync CLI derives it), and the WARN says to regenerate the catalog; a row that is not live fails the submit with OpenRouter's "does not have a :batch endpoint" as before.
- A clean batch no longer stores every verdict in the `${id}:collect` step result (92 KB for 27 items): the collect row holds counts, the failed items and the repair feedback, and each item's verdict lives on its own `${id}:${itemId}` row, completed or failed, as on the realtime path. A replay that finds an item row missing (the process died between the collect and that row) re-fetches the batch results; the logger records accounting once per batch id.
- Structured-output schemas are made portable per target. OpenAI's strict structured outputs (native, and through OpenRouter's chat and `:batch` endpoints) reject the `oneOf` that `z.discriminatedUnion` emits, and Gemini drops it; every JSON `responseFormat` sent to an OpenAI, OpenRouter or Google model is rewritten at the model boundary (`oneOf` → `anyOf`, `additionalProperties: false` for OpenAI, `$schema` stripped) through an AI SDK middleware, so `generateObject`, `generateText` + `Output.object`, `streamText`, every `ctx.step.ai.*` call and the OpenAI/OpenRouter batch bodies all send a schema the target accepts while validation stays on the original Zod schema. Verified live on Google (`gemini-2.5-flash-lite`) and OpenRouter (`openai/gpt-5-nano`, Azure-OpenAI upstream) with a nested discriminated union; the raw provider path still fails with `'oneOf' is not permitted`.

**Fixes from the second consumer round (1.0.0-alpha.1):**

- Google batches send a `responseSchema` the batch endpoint enforces and that keeps unions. Probed live: Gemini's `batchGenerateContent` ignores `generationConfig.responseJsonSchema` for a small schema and rejects it per request (`code 3 "Request contains an invalid argument"`) for a real one, so alpha.1's fix answered nothing; the provider's own OpenAPI conversion forwards `oneOf` (which Gemini's `Schema` lacks) and drops array bounds, which is why alpha.0 flattened discriminated unions. The engine now converts the JSON Schema itself — `oneOf`/`anyOf` to `anyOf`, `const` to `enum`, `null` branches to `nullable`, `$defs` inlined, bounds kept — and substitutes it at the fetch boundary as before. Verified live against a 7 KB schema with nested discriminated unions: the batch reply validates against the original schema.
- Batch failure visibility: the poll logs a WARN when a settled batch reports failed requests, and the "more than half failed" WARN covers provider-side failures as well as schema validation, naming the class and the first error. Batch accounting rows store the model's reply — its raw text when it failed validation — and `metadata.batchDurationMs` (the batch wall time) instead of repeating it as a per-row `durationMs`.
- A batch is polled and collected through the transport its stored refs name, not whatever the registry resolves for the model key at poll time; changing `batchProvider` while a batch is in flight no longer strands the run with "belongs to unknown provider".
- Vendor resolution reads `ModelConfig.provider`: a `provider: "google"` entry is the Google vendor whether its `id` is the bare model id or the catalog slug, and the batch and realtime paths both strip the vendor prefix — one entry serves `map` batches and their realtime repair (the slug 404ed on the Google API before). The missing-vendor-SDK fallback to OpenRouter also engages on workerd, whose dynamic-import error is `No such module "@ai-sdk/openai".` without a code.
- A failed step is re-executed on the next job attempt: a retry of a stage whose last attempt threw re-opens every `run` step and every `map` item that ended `failed` (their ledger rows keep the failure but are re-claimed), so a `${id}:submit` that hit a 503 or an item that exhausted its repair budget gets a fresh call instead of replaying the stored failure; completed steps still replay, and a poll of the same attempt still answers failures from the ledger. Map verdicts are stored on the item's `failed` row itself (no more `${id}:${itemId}:failed` memo step). `WorkflowStage.attempt` now counts job retries too (0 on the first execution).
- `stage:retrying` (`attempt`, `maxAttempts`, `error`) is emitted for a retried attempt; `stage:failed` is emitted only when the stage row becomes `FAILED`.
- Host job results carry the retry contract: `executeJobWithHeartbeat` and the serverless host's `handleJob` return `willRetry`, `attempt`, `maxAttempts` and `retryDelayMs` (the built-in transports' `2^attempt` seconds), so a push transport whose `fail()` cannot re-enqueue (a Cloudflare Queue consumer) retries the message itself; the README states the contract. Malformed job messages (no `payload`, no `workflowId`) are validated up front and failed as dead jobs (`dead: true`) instead of throwing from inside `job.execute`.
- A stage that fails terminally from the poll path (a step retry that ran inside `stage.pollSuspended`, a `checkCompletion` error, a wait past its deadline) finalises its `job_queue` row (`FAILED`, `completedAt`) instead of leaving it `SUSPENDED`.
- A stage waiting on a leased in-flight step after a crash announces `stage:suspended` / `workflow:suspended` once, not on every 5s poll: the step id is the identity of the wait.
- `PrismaWorkflowPersistence.withTransaction` re-applies every constructor option (`statusEnumName`, `now`, ...) to the transactional clone; `run.claimPending` inside a transaction no longer fails with `42704 type "Status" does not exist` on a schema that names the enum differently.
- `PrismaJobQueue.dequeue` on Postgres fails a row whose `payload` is NULL as a dead job (logged with the job id) and takes the next row instead of throwing and aborting the tick.
- Failed `generateObject`/`generateText` calls log the tokens (and cost) the thrown `NoObjectGeneratedError` carries instead of 0/0, and `WorkflowRun.totalCost`/`totalTokens` are rolled up on `FAILED` runs as well as `COMPLETED` ones.
- `workflow-engine-codemod` runs when invoked through a symlinked bin (`npx`, `pnpm exec`, a pnpm-linked `node_modules` path): the "am I the entry point" guard compares real paths.
- `workflow-engine-sync` output is 1.0-clean: it emits absolute batch prices (the native vendor discount applied to the model's own prices when the catalog has no `:batch` sibling) instead of `batchDiscountPercent`, the field codemod rule 7 flags, and stamps `batchProvider: "openrouter"` on models only OpenRouter can batch.
- Reference: step results are small JSON (large payloads go to the blob store or artifacts, the step returns the key); the retry semantics above are documented in 12-durable-steps.md, 08-common-patterns.md and the 0.13 → 1.0 migration guide.

Retry classification: `NonRetryableError` and `retryIf`.

- **`NonRetryableError`** (with `isNonRetryableError`, which recognises it across bundled copies) fails a stage attempt terminally when thrown from a stage or a `ctx.step.run` body: no step `retries`, no job retry, no poll retry. Pass the original error as `cause`. An AI map item whose model call throws it fails at once, with no in-process retry or repair.
- **`StepRunOptions.retryIf(error, { attempt })`** decides per error, synchronously. `false` stops the step's own `retries`, and the stage receives a `NonRetryableError` with the original as `cause`. Anything else, a predicate that throws included, leaves the error retryable, as before (a throw or an object return is logged). A predicate that returns or throws a Promise breaks its synchronous contract: the engine attaches a no-op handler to a plain native Promise where it can, and if that Promise rejects and the engine cannot attach a handler, the rejection is the application's own unhandled rejection, as anywhere else in stage code. Without it a step retries every error but `NonRetryableError`.
- **The stage classifier is main's, plus the `NonRetryableError` brand.** `isRetryableStageError` (now exported from `@bratsos/workflow-engine/kernel`) still rejects a Zod error of the engine's own zod and a duplicate step key, exactly as before, and now also a value carrying the `NonRetryableError` brand, read as one symbol property after those checks. An expired durable wait and an `onReclaim: "fail"` refusal carry that brand as the execution that records them throws them, so they no longer spend job attempts on the same error (`isNonRetryableError` is true for them). The engine reads no name, message, cause or other field of a thrown value to classify it, and records every error text exactly as before.
- **The step ledger stores what it stored before.** A failed step row holds the message only. A replayed step failure is classified as on main: it comes back as a plain `Error` with the stored message (or `StepTimeoutError` for the step's timeout text), with no brand, so a `NonRetryableError` or a `retryIf` refusal is terminal only in the execution that threw it, and a replay with `retries` left runs the body again. Stage retries re-open failed steps and `onReclaim` decides takeovers exactly as before. A terminal verdict ends the job exactly as an exhausted final attempt does: the stage is FAILED, the queue row fails, the run fails, and a later delivery of the job (a lost acknowledgement, a lost lease) meets that FAILED stage and ends as a dead job with the stored error, exactly as after an exhausted final attempt: no step runs again and no retry is scheduled.
- **Rolling deploys.** A terminal verdict (`NonRetryableError`, a `retryIf` that returns `false`) is honoured once every host runs this release. A host still on an earlier release that recovers a job (after a lost lease or a lost failure acknowledgement) runs it as that release does: it can run the body again, even past the queue's budget, which limits only the decision to schedule another retry, so completed steps and provider calls can run again. The dead-job end after a lost acknowledgement requires the recovering host to run this release.
- **A throwing `checkCompletion` is unchanged.** It fails the stage and the run on that poll.
- **Dead jobs.** `job.execute` throws `JobTargetMissingError` (now exported, with `isJobTargetMissingError`) when the job's workflow, stage or run is missing, with the same text as before and the command's `target`. The host helper acknowledges a job as dead in two cases:
  - the branded error, whose `target` is that job's workflow, stage and run;
  - otherwise, any thrown value (an `Error` or a plain object) whose `name` is `JobTargetMissingError` or `Error` and whose `message` is exactly one of the three texts for that job: `Workflow <workflowId> not found in registry`, `Stage <stageId> not found in workflow <workflowId>` or `WorkflowRun <workflowRunId> not found`. This covers the plain `Error` an earlier release's kernel throws and an error decoded from JSON, and also any other error with that name and text: the stage text does not name the run, and the run text names neither the workflow nor the stage.

  An error with any other name or text, or the branded missing target of another dispatch made inside the job, is rethrown. Without the brand, a nested dispatch's missing workflow with the same id cannot be told apart from the job's own.

No schema change.

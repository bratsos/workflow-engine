`run.cancel` cancels the provider batches a run created.

- **The bug:** cancelling a run left the batches its `ctx.step.ai.map` steps had submitted running at the provider, and billing, until they ended.
- **The fix:** after the cancel commits, `run.cancel` finds every batch the run created across all its stage records (the `${id}:submit` steps, recognised by their stored submit record rather than the id alone, and refs a legacy async-batch stage persisted in `suspendedState.metadata.batchRefs`) and cancels each one that has not ended. A transport is built from the stored ref (`provider`, `modelId`) with the environment's credentials, so the process that dispatches the cancel need not be the one that ran the stage; `createKernel({ services: { batchModels } })` overrides how it is found.
- **Outcomes:** `RunCancelResult.batches` reports one outcome per batch: `cancelled`, `already-terminal`, `unsupported` (the transport has no cancel call), `unavailable` (no transport could be built in this process), `failed`, `unrecorded`, `unverified` or `held` (another sweep holds the submit step until `heldUntil`; repeat `run.cancel` after then). A batch that may still be running is also a WARN log on the run. The run ends `CANCELLED` whatever a provider answers.
- **Providers:** OpenAI (`POST /v1/batches/{id}/cancel`), Anthropic Message Batches (`POST /v1/messages/batches/{id}/cancel`) and Gemini (`POST /v1beta/batches/{name}:cancel`) cancel through the vendor SDK's `doCancelBatch`. OpenRouter documents no cancel call, so its batches are `unsupported`. New: optional `EngineBatchModel.cancel`, `EngineBatchCancelResult`, optional `AIBatch.cancel`, `resolveBatchModelForRef`.
- **Recovery:** `cancelled` still means "this command moved the run to CANCELLED", so a second `run.cancel` on a CANCELLED run answers `cancelled: false`; it now also re-reads every batch of the run and retries each provider cancel that did not take effect, and reports them in `batches`. A FAILED run keeps its batches, because `run.redrive` re-adopts a live one.
- **Redrive:** a batch that is cancelling or cancelled is never adopted or waited on. When every batch of a `${id}:submit` row is cancelled (or found already cancelled), the engine tombstones the stored submit record and re-opens the step, so `run.redrive` creates a new batch on every transport, with no `onReclaim` and no adoption search; the new batch's poll and collect steps are `${id}:poll.1` and `${id}:collect.1`, so rows the cancelled batch left behind are not replayed and the old wait's deadline does not apply. A batch that was not confirmed cancelled keeps the conservative behaviour (the live batch is waited on; a transport that cannot adopt throws `BatchNotAdoptableError`).
- **Running stages:** no durable step body starts once the stage's signal reports a cancel (`ctx.step.run` and every step built on it throw the stage's `StageAbortedError` before the body and write no row, so a redrive does not count an attempt; a lost lease keeps its behaviour). `ctx.step.ai.map` cancels a batch whose submit was in flight when the cancel landed. A body whose signal had not fired can still create a batch after `run.cancel` read the ledger, so every place where a handler that ran a stage body finds the run CANCELLED sweeps its batches too: the four ghost exits of `job.execute` that follow a body (the fenced failure, suspension and completion commits, and the status re-check before a suspension), a `stage.pollSuspended` replay whose stage the cancel moved while its body ran, and both CANCELLED branches of the claim a replay ends in.
- **Safe against a redrive:** the sweep is tied to the cancelled run generation (`redriveCount`) and checks it before it reads, after it has taken hold of the submit rows (leased and fenced, so a replay waits and the ledger reset leaves the lease alone) and before each provider call; a sweep held up past a `run.redrive` does nothing and releases the rows untouched.
- **One sweep per row:** taking hold of a submit row is a takeover at `attempt + 1` with a lease taken at that moment, and every later write of the sweep is pinned to that attempt, so two sweeps cannot both hold a row and a sweep whose hold was taken over writes nothing more. The tombstone moves with the attempt.
- **Intent before the request:** before each provider cancel the sweep records `cancelIntent` on the row; nothing is sent unless that write applied, the run generation is unchanged, the call fits inside the hold and the budget is not spent. A batch whose answer is unknown (an error, a timeout, a process that died) stays in the intent and the row is re-opened, so nothing continues on a batch a cancel may have reached. The step's own cancel of a batch it created after the run was cancelled records the intent the same way.
- **A sweep that dies:** a repeated `run.cancel` takes the row over and repeats the cancel, ending in the state an uninterrupted sweep reaches; the ledger reset leaves the row alone; a redriven submit step sends the cancel again for every batch in the intent before it does anything (`EngineBatchStatus.cancelled` reports cancelling or cancelled batches): confirmed cancelled batches are replaced on any transport, ended ones collected, and when the cancel cannot be completed the step fails retryably with a WARN and keeps the intent. A sweep that died before it sent anything leaves no intent, and the stage continues on the recorded batches with no adoption search and no refusal. Until the dead sweep's hold ends, every `run.cancel` and `run.redrive` reports the step as `held` with `heldUntil` (`RunCancelResult.batches`, and the new optional `RunRedriveResult.batches`), one outcome per batch the row lists, and the WARN says to repeat after that time; this includes a sweep that lost a row to another sweep while taking hold of it.
- **The failure write keeps the submit record:** a failed submit step's failure write leaves the row's `result` alone, so the engine's submit record (the partial record that keeps accepted partitions reachable, the tombstone, a sweep's fence) survives it, the retry's re-open and the ledger reset.
- **Ownership:** only a submit record carrying the engine's own marker (`externalKey` equal to its row's) is cancelled. An ordinary step that memoises a foreign handle, and every record written before this release, is reported as `unverified` and left alone. A submit step that holds no handle (executing, or failed before recording one) is reported as `unrecorded` with its external key instead of being skipped.
- **No batch becomes unreachable:** when a later partition of a submit is rejected, the partitions the provider accepted are recorded in the failed row (cancelled at once if the run was cancelled), `run.cancel` finds them, and the retry resumes after them (`AIBatchSubmitOptions.existingRefs`). A batch listed by several owners is cancelled once and every owning row is finalised. The batches the engine cancelled are kept in the record (`cancelledBatchIds`) and never adopted, also on Gemini, whose cancel is asynchronous (`EngineBatchModel.adopt` takes `excludeBatchIds`).
- **Submit outcomes are pinned to the claimed attempt:** every outcome write of a `${id}:submit` row (success, failure, cancellation, refusal) applies only at the attempt the execution claimed, so no execution can replace or drop a sweep's hold, intent or tombstone that it did not read in the same compare-and-set. A submit body whose lease was taken over parks on a recorded outcome or throws `StepLeaseLostError`. Other `run` steps keep first write wins.
- **A body that lost its row cancels what it created:** the batches it created that the row does not list are recorded as owed a cancel (`cancelOwed`, when nothing holds the row) and cancelled; a cancel the body did not complete (its process stopped before the request left) is completed by the next `run.cancel`, the next `run.redrive`, the step's next execution if the row is still open, and, on a completed row or a failed one with no retry left, the next replay of the stage that reads it (every poll and collect of the stage replays the submit step), and the id moves to `cancelledBatchIds` once the provider acknowledges it. One case is left: a body that records the owed id after the stage's last replay (the stage has completed or failed) and whose process stops before the request leaves. Nothing reads the row again unless the run is redriven; the batch runs until it ends, named by id in the row's `cancelOwed` and by the step's external key in the stage's WARN that the execution lost the step. The replays are bounded by what the row records (`cancelRetry`): after a failed attempt the next one waits 1 minute, then 2, 4 and so on, at most 1 hour, and a WARN is written only when the kind of failure changes; the step's own execution, `run.cancel` and `run.redrive` still send at once. A provider with no cancel call (OpenRouter) is settled once: the id moves from `cancelOwed` to `noCancelBatchIds` (never sent again, never adopted) with one WARN that says to cancel it in the provider's console if it has one or let it end. An exclusion write whose answer is lost is read again, and a batch the row already records as excluded is still cancelled by the execution that created it; a body whose own cancel (after a `run.cancel`) loses the row hands its batch to the same cleanup instead of warning. When a sweep holds the row they are cancelled without a write, and when the row is gone they are cancelled. When another live execution holds the row they are left for it to adopt, with a WARN, on a transport that can search (OpenAI, Gemini), and cancelled on one that cannot (Anthropic, OpenRouter), where that execution never lists them. New: optional `AIBatch.canAdopt`.
- **Spilled step results are written once per key:** a durable step result above the spill threshold now goes to a new blob key on every write (`<stageRecordId>/<stepId>/<uuid>.json`), and a write that does not apply deletes its blob, so an execution that loses a row can no longer replace the blob the winner's record names (it used to, leaving the winner's batch unlisted and the loser's listed). Rows written before this release keep their `<stepId>.json` key and are read as before.
- **`run.cancel` cancels the generation it read:** its run write is fenced on the version it read; a cancel held up while another cancel and a `run.redrive` ran reads the run again, so it cancels and sweeps the generation it actually ends (before, it ended the redriven run and swept the old generation, reporting nothing).
- **A sweep that sends nothing leaves no intent:** the release keeps the intent the row carried before the hold and the batches a request left for; one the sweep recorded but did not send (a redrive landed, the budget ran out) is dropped, so a redriven step does not cancel and replace a batch no cancel reached. A batch whose row a redrive deleted under the sweep is reported as such ("nothing will cancel this batch") rather than as left for a later sweep.
- **`run.cancel` ends only stages that have not ended:** each stage write is fenced on the version it read and re-read when that version moved, so a stage a `job.execute` completed first stays `COMPLETED`, on Postgres and SQLite.
- **Bounded:** the provider calls take at most 30 s per batch and 60 s per sweep (`KernelServices.batchCancelTimeouts`); a batch not reached is `failed`.
- **Docs:** an `unrecorded` step stays `unrecorded` until the lease of the execution that holds it expires (5 minutes, the default step lease), even when its row already lists the batch; repeat `run.cancel` after that. The batch operations guide says per provider how to find a batch from what a WARN records: by id, by the external key where the provider stores it (OpenAI `metadata`, Gemini `displayName`), and by creation time and request count where it does not (Anthropic, OpenRouter).
- **OpenRouter:** the batch transport defaults to the documented base URL `https://openrouter.ai/api/v1` (it was `/api/beta`, which the documentation no longer lists); pass `baseURL` to keep another.
- **A redrive from the start completes the cancels it would make unreachable:** a batch whose cancel was asked for on a submit row the redrive deletes (a sweep held it, or recorded a cancel on it), a batch a row owes a cancel, and, on a `CANCELLED` run, every batch of a stage record it deletes whose stage had not completed (the engine-owned refs of its submit rows and a legacy stage's `suspendedState` refs, unless recorded as cancelled; a sweep still running can record its cancel after the redrive read the row) are cancelled after the commit and reported in `RunRedriveResult.batches` with the provider's answer. Before the commit, a WARN on the run names every batch the redrive is about to cancel; after it, one line per batch gives the outcome (INFO when answered, a WARN otherwise), so a redrive that stops in between leaves each batch named with what to do; a sweep that finds its row deleted sends the cancel with no record. WARNs that name a batch are written on the run (a stage-scoped log is deleted with its stage record), a failed log write is retried and then printed with `console.error`, and they advise repeating `run.cancel` only while the run is still `CANCELLED`.

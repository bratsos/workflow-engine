The run detail groups each stage's history by attempt. A new "Attempts by stage" section lists every attempt of every stage with when it started and ended, why it began (first run, job retry, retry inside `stage.pollSuspended`, a rerun after a terminal outcome, or a re-delivery), how it ended, its error, its stage events, and the steps that last changed during it. A retry inside `stage.pollSuspended` appears as an attempt boundary like a job retry. A `run.cancel` ends the open attempt as cancelled (the `workflow:cancelled` event) and a redrive (`workflow:started`) makes the next `stage:started` a rerun. Each attempt is a native disclosure control. A stage whose execution started again with no event ending the previous one (a worker crash and re-delivery, a reaped lease) shows the earlier execution as *No end recorded* and the re-delivery as its own attempt, with its steps placed by time only; a stage failed by `run.reapStuck` while it waited for a retry shows a failed attempt that never started. When a run's events are purged, past retention, contradict themselves or disagree with the stage's row, the stage falls back to its latest attempt and says per-attempt history is unavailable.

`RunDetail` gains an optional `stageEvents: { events: StageEvent[]; after: number; lastSequence: number; complete: boolean; more: boolean }`: the run's stage lifecycle events and its `workflow:started` and `workflow:cancelled` events, read apart from the 200-row `events` list with only the stage id and the error extracted from each payload, the error text capped at 2,000 characters. `RunDetailOptions.stageEventsAfter` (`GET /api/runs/:id?stageEventsAfter=N`) returns only the events after a sequence: the page keeps what it has read and asks for the rest, so a refresh reads the run's new outbox rows and its cost does not grow with the run's event count; a read returns at most 2,000 events and the page asks again until it has caught up. Custom `ConsoleReadPort` implementations keep compiling and keep working without it. `createInMemoryConsoleReadPort` accepts `fixtures.stageEvents`. The run detail now issues up to nine statements in one transaction instead of six. No schema change.

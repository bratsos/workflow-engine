The run detail groups each stage's history by attempt. A new "Attempts by stage" section lists every attempt of every stage with when it started and ended, why it began (first run, job retry, retry inside `stage.pollSuspended`, or a rerun after a terminal outcome), how it ended, its error, its stage events, and the steps that last changed during it. A retry inside `stage.pollSuspended` appears as an attempt boundary like a job retry. A `run.cancel` ends the open attempt as cancelled (the `workflow:cancelled` event) and a redrive (`workflow:started`) makes the next `stage:started` a rerun. Each attempt is a native disclosure control. When a run's events are purged, past retention, cut off, or disagree with the stage's row, or a stage's execution started again with no event ending the previous one (a worker crash and re-delivery, a reaped lease), the stage falls back to its latest attempt and says per-attempt history is unavailable.

`RunDetail` gains an optional `stageEvents: { events: StageEvent[]; after: number; lastSequence: number; complete: boolean }`: the run's stage lifecycle events and its `workflow:started` and `workflow:cancelled` events, read apart from the 200-row `events` list with only the stage id and the error extracted from each payload, the error text capped at 2,000 characters. `RunDetailOptions.stageEventsAfter` (`GET /api/runs/:id?stageEventsAfter=N`) returns only the events after a sequence: the page keeps what it has read and asks for the rest, so a refresh reads the run's new outbox rows and its cost does not grow with the run's event count. Custom `ConsoleReadPort` implementations keep compiling and keep working without it. `createInMemoryConsoleReadPort` accepts `fixtures.stageEvents`. The run detail now issues up to eight statements in one transaction instead of six. No schema change.

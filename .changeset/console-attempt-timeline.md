The run detail groups each stage's history by attempt. A new "Attempts by stage" section lists every attempt of every stage with when it started and ended, why it began (first run recorded, job retry, retry inside `stage.pollSuspended`, a rerun after a redrive, started again after it ended, or started again while the previous execution had no recorded end), how it ended, its error, its stage events, and the steps that last changed during it. Each attempt is a native disclosure control. A `run.cancel` ends the open attempt as cancelled (the `workflow:cancelled` event) and a redrive (`workflow:started`) makes the next `stage:started` a rerun. A stage that started again with no event ending the previous execution shows that execution as *No end recorded* and lists causes that leave this record without picking one; a stage failed by `run.reapStuck` while it waited for a retry shows a failed attempt that never started.

The history is built from the events the run's outbox still holds, and the page says so in one line wherever it shows one. The page uses a stage's events only when they form an unbroken range from the run's first outbox row (its `workflow:created`), which finds every row removed from the start or the middle. Rows removed from the end are found only when what remains contradicts the run's or the stage's row: a store numbers a run's next row one past the highest it holds, so after the run writes again the range is unbroken, and a crash re-delivery or a poll retry recorded only in removed rows is not shown. Nothing in the engine deletes outbox rows (`run.purge` removes the run and leaves them); only SQL such as an operator's pruning job does. The checks, none resting on the numbering: the run's own events follow the engine's order (every redrive's `workflow:started` after a run end), record exactly the run's redrive count and end in its status; the stage's row agrees with them (its status, its `attempt` as the recorded executions and each redrive mode give it, `startedAt`, `completedAt` and error). Otherwise the stage falls back to its latest attempt and says why: rows missing (removed by SQL, including after every row was removed), no row of the run retained, still reading (or, with polling off, reading no more until it resumes), fewer retained redrives than the run's row counts, run events that contradict the engine's order or the run's row, no events from the reader, no lifecycle event of a stage whose row says it ran, events that contradict each other, or a disagreement with a named field of the stage's row. Labels speak of recorded events ("First run recorded", "2 recorded attempts"), and a stage shows that no start of it is recorded only when its row's status and `attempt` say it has not run. Only what every store writes alike is read: before a stage's first start the Prisma store stamps the row's `startedAt` with its creation time (rows written by earlier releases have it too) and the in-memory store leaves it null, so `startedAt` is compared only after a retained `stage:started` with no redrive since. After a redrive a row's status and error may be the ones it kept, with a later cancel applied. One `job.execute` writes a start and that execution's end under one causation id; an end written under an earlier start's id (an execution that kept running after a cancel or a lost lease) cannot be attributed, and the stage says so.

`RunDetail` gains an optional `stageEvents: { events: StageEvent[]; after: number; lastSequence: number; complete: boolean; more: boolean }`: the run's stage lifecycle events and its `workflow:created`, `workflow:started`, `workflow:completed`, `workflow:failed` and `workflow:cancelled` events, read apart from the 200-row `events` list with only the stage id and the error extracted from each payload, the error text capped at 2,000 characters. `RunDetailOptions.stageEventsAfter` (`GET /api/runs/:id?stageEventsAfter=N`) returns only the events after a sequence: the page keeps what it has read and asks for the rest. A read covers at most 10,000 outbox sequences and returns at most 2,000 events, so its cost is bounded whatever the run's size, in every state of the table's statistics (none, the empty table's, current, stale), as the tests measure on Postgres and SQLite; the run's highest sequence is read as `ORDER BY sequence DESC LIMIT 1`, which `max(sequence)` was not under stale statistics. The page asks again at once until it has caught up, at most four reads per poll interval (a run of 400,000 sequences takes 40 reads, about 50 seconds at the default 5-second interval), as long as each read advances and polling is on; with polling off the page makes no request on its own. `complete` is false for a first read that finds no row. A custom `ConsoleReadPort` without `stageEvents` keeps compiling and working; its run detail says, for every stage, that per-attempt history is unavailable because the reader does not provide stage events. `createInMemoryConsoleReadPort` accepts `fixtures.stageEvents`. `StageEvent` gains an optional `causationId`. The run detail now issues up to eighteen statements in one transaction on Postgres (twelve on SQLite) instead of six, `REPEATABLE READ` on Postgres so they see one moment (inside a caller's transaction, that transaction's isolation decides; a reader that does not read at one moment makes a stage that changed during the read unavailable, naming the field, until the next poll). `listRunEvents` reads the first row after the cursor and then the `limit` sequences from it, so its plan no longer depends on the table's statistics; it may return fewer rows than `limit` across removed rows or a gap, and only an empty answer means none remain; an `afterSequence` past the sequence column's range returns none instead of an HTTP 500. The run detail asks the client for `REPEATABLE READ` through `$transaction`'s `isolationLevel` option and sends no `SET TRANSACTION`, so a read inside a Prisma 7 transaction no longer makes Postgres log an error per poll; inside a caller's transaction the reader restores the `statement_timeout` it set. The read's transaction limits follow `statementTimeoutMs` (twenty times it, and none with 0, where Prisma's 5-second default ended slow reads with HTTP 500; each capped at 2,147,483,647 ms, the longest timer Node keeps), the wait for a connection is `statementTimeoutMs` on every Prisma major (on Prisma 8, whose `fromPrisma8` takes no `maxWait`, the reader bounds it itself; on SQLite this is also the wait behind another transaction, so a read queued behind one answers 504 `query_timeout` with `limit: "connection"`, and with 0 it waits), and a transaction the client gave up on answers 504 `query_timeout`. `ConsoleQueryTimeoutError` gains `limit` (`"statement_timeout"`, `"transaction"` or `"connection"`), and its message names the limit that fired. `listRunEvents` throws `ConsoleBadRequestError` for an `afterSequence` that is not a number on every port. A run's first start written as two `workflow:started` rows (`run.transition` dispatched before `run.claimPending`) reads as one start instead of making every stage unavailable. The annotations page is read by the run's `("workflowRunId", "createdAt")` index in every state of the table's statistics and fetches at most a page of rows, also when the page ends inside a group of annotations that share a time (the server still reads that group through the index). On Postgres it reads through cursors inside the read's transaction, so a pooler must give the transaction one server connection (a transaction-scoped connection; PgBouncer is untested); a client with no `$transaction` that is not a transaction client gets the same rows from plain statements. The steps page is read 1,000 stages per statement, so a run of more stages than a statement takes parameters reads correctly; on SQLite it orders the steps by the stage ids it read, with no join to the stages table (statistics taken while that table held one row planned a scan of it for every step). On SQLite the reader names only a full index whose leading columns serve the statement, and a read whose named index has gone runs again without one. The steps page reads the steps of the run's stages by their ids and the logs page by the run's index, so no statement reads another run's rows; each sorts every step or log of the run, at most a page per row, at the cost the docs state. No schema change.

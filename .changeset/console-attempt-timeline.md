The run detail groups each stage's history by attempt. A new "Attempts by stage" section lists every attempt of every stage with when it started and ended, why it began (first run recorded, job retry, retry inside `stage.pollSuspended`, a rerun after a redrive, started again after it ended, or started again while the previous execution had no recorded end), how it ended, its error, its stage events, and the steps that last changed during it. Each attempt is a native disclosure control. A `run.cancel` ends the open attempt as cancelled (the `workflow:cancelled` event) and a redrive (`workflow:started`) makes the next `stage:started` a rerun. A stage that started again with no event ending the previous execution shows that execution as *No end recorded* and lists causes that leave this record without picking one; a stage failed by `run.reapStuck` while it waited for a retry shows a failed attempt that never started.

The history is built from the events the run's outbox still holds, and the page says so in one line wherever it shows one. The page uses a stage's events only when they form an unbroken range from the run's first outbox row (its `workflow:created`), which finds every row removed from the start or the middle. Rows removed from the end are found only when what remains contradicts the run's or the stage's row: a store numbers a run's next row one past the highest it holds, so after the run writes again the range is unbroken, and a crash re-delivery or a poll retry recorded only in removed rows is not shown. Nothing in the engine deletes outbox rows (`run.purge` removes the run and leaves them); only SQL such as an operator's pruning job does. The checks, none resting on the numbering: the run's own events follow the engine's order (every redrive's `workflow:started` after a run end), record exactly the run's redrive count and end in its status; the stage's row agrees with them (its status, its `attempt` as the recorded executions and each redrive mode give it, `startedAt`, `completedAt` and error). Otherwise the stage falls back to its latest attempt and says why: rows missing (removed by SQL, including after every row was removed), no row of the run retained, still reading (or, with polling off, reading no more until it resumes), fewer retained redrives than the run's row counts, run events that contradict the engine's order or the run's row, no events from the reader, no lifecycle event of a stage whose row says it ran, events that contradict each other, or a disagreement with a named field of the stage's row. Labels speak of recorded events ("First run recorded", "2 recorded attempts"), and a stage shows that no start of it is recorded only when its row was never stamped by a start.

`RunDetail` gains an optional `stageEvents: { events: StageEvent[]; after: number; lastSequence: number; complete: boolean; more: boolean }`: the run's stage lifecycle events and its `workflow:created`, `workflow:started`, `workflow:completed`, `workflow:failed` and `workflow:cancelled` events, read apart from the 200-row `events` list with only the stage id and the error extracted from each payload, the error text capped at 2,000 characters. `RunDetailOptions.stageEventsAfter` (`GET /api/runs/:id?stageEventsAfter=N`) returns only the events after a sequence: the page keeps what it has read and asks for the rest. A read covers at most 10,000 outbox sequences and returns at most 2,000 events, so its cost is bounded whatever the run's size; the page asks again at once until it has caught up, as long as each read advances and polling is on; with polling off the page makes no request on its own. `complete` is false for a first read that finds no row. A custom `ConsoleReadPort` without `stageEvents` keeps compiling and working; its run detail says, for every stage, that per-attempt history is unavailable because the reader does not provide stage events. `createInMemoryConsoleReadPort` accepts `fixtures.stageEvents`. The run detail now issues up to nine statements in one transaction instead of six. No schema change.

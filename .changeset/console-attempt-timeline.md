The run detail groups each stage's history by attempt. A new "Attempts by stage" section lists every attempt of every stage with when it started and ended, why it began (first run, job retry, retry inside `stage.pollSuspended`, a rerun after a redrive, started again after it ended, or started again while the previous execution had no recorded end), how it ended, its error, its stage events, and the steps that last changed during it. Each attempt is a native disclosure control. A `run.cancel` ends the open attempt as cancelled (the `workflow:cancelled` event) and a redrive (`workflow:started`) makes the next `stage:started` a rerun. A stage that started again with no event ending the previous execution shows that execution as *No end recorded* and lists causes that leave this record without picking one; a stage failed by `run.reapStuck` while it waited for a retry shows a failed attempt that never started.

The page uses a stage's events only when they cover the run from its first outbox row with none missing and the stage's row agrees with them (its status, `attempt` count, `startedAt`, `completedAt` and error). Otherwise the stage falls back to its latest attempt and says why: rows missing (purged or past retention), no row of the run retained, still reading, no events from the reader, no lifecycle event of a stage whose row says it ran, events that contradict each other, or a disagreement with a named field of the stage's row. A stage is shown as not started only when its row was never stamped by a start.

`RunDetail` gains an optional `stageEvents: { events: StageEvent[]; after: number; lastSequence: number; complete: boolean; more: boolean }`: the run's stage lifecycle events and its `workflow:started` and `workflow:cancelled` events, read apart from the 200-row `events` list with only the stage id and the error extracted from each payload, the error text capped at 2,000 characters. `RunDetailOptions.stageEventsAfter` (`GET /api/runs/:id?stageEventsAfter=N`) returns only the events after a sequence: the page keeps what it has read and asks for the rest. A read covers at most 10,000 outbox sequences and returns at most 2,000 events, so its cost is bounded whatever the run's size; the page asks again at once until it has caught up, as long as each read advances. `complete` is false for a first read that finds no row. A custom `ConsoleReadPort` without `stageEvents` keeps compiling and working; its run detail says, for every stage, that per-attempt history is unavailable because the reader does not provide stage events. `createInMemoryConsoleReadPort` accepts `fixtures.stageEvents`. The run detail now issues up to nine statements in one transaction instead of six. No schema change.

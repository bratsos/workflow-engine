Deliver outbox events at least once with expiring owner-guarded claims. Delivery can duplicate whenever the sink effect happens without a durable acknowledgement. Examples include a crash or write error after acceptance, an emit in flight at expiry, a sink that commits and then rejects, and partial plugin success. Sinks and plugins can deduplicate using the provided outbox event ID. A run and sequence order its events but are not a permanent key: deleting the newest rows by SQL can permit a sequence to be reused. Order is decided at claim time. A replayed dead letter is delivered after later events of its run already claimed or published before replay. After replay, later unclaimed events wait behind it. Failed events are retried up to the budget and then require `plugin.replayDLQ`. Engine progress remains independent of the sink.

Custom persistence adapters must implement the new outbox methods. Stop all alpha.20 flushers and close their connections before the schema upgrade. On SQLite stop every process using the file, close its clients, and upgrade the schema in a separate process. Add the nullable `deliveryClaim` field and all three outbox indexes in one schema migration. The hand-written form in the migration guide runs inside `BEGIN IMMEDIATE`…`COMMIT` (`BEGIN`…`COMMIT` on PostgreSQL), so a process killed between its statements leaves the schema unchanged; the guide also says how to finish a partial state left by statements run outside a transaction. Flushers find run heads from the current rows and rotate past the last run served. Existing rows need no backfill. Legacy publication stamps remain published. A caller-owned transaction defers delivery to a root-client flush after commit.

The Prisma claim and unpublished inspection support a client with either raw-read method. On SQLite the date-storage check runs before outbox operations, including completion, retry, and append.

One statement claims a page: one head per available run, then each claimed run's next live events up to an equal share of the page. A run's events reach the sink in sequence order and runs concurrently; the claim returns only the rows it now owns, and a run's acknowledgements are written together when its share of the page ends. The rank of a claimed run is its position in the rotation walk, saturating at the largest `BIGINT`, so concurrent cold flushes continue after the furthest run any of them claimed. The claim needs `$queryRaw` or `$queryRawUnsafe` on PostgreSQL and SQLite, and a root without either is refused when the persistence is built with `OutboxClaimUnsupportedError` (`OUTBOX_CLAIM_UNSUPPORTED`). Fencing costs statements: a page of eight events takes 6 driver statements on PostgreSQL against 1 before, and 3 on SQLite against 9 before. In a local Prisma 7 benchmark such a page took 3.1 to 3.5 ms on PostgreSQL 16 against 0.5 to 0.9 ms, and 1.1 to 1.3 ms on SQLite against 2.2 to 2.9 ms; eight one-event flushes took 19.7 ms against 3.2 ms on PostgreSQL and 10.0 ms against 3.3 ms on SQLite. An idle SQLite flush reads one row and takes no write lock. New optional persistence method `completeOutboxDeliveries` writes the acknowledgements in one statement.

Autocommit root wrappers without `$transaction` can flush and append an atomic batch. Wrap caller-owned clients with their transaction marker intact or pass `transactionView: true`. PostgreSQL honours `skipInteractiveTransactions: true` for claims. That shape, a root without `$transaction` and a wrapper whose transaction view has no raw read run the claim without its transaction-local planner settings, so the plan follows the statistics; run `ANALYZE outbox_events` after bulk loads there. A durable cursor in the outbox rotates service across fresh adapters. Different runs in a page can reach the sink concurrently.

SQLite writes queued through the Prisma adapters during an active transaction now wait for it and then run, whether it commits or rolls back. Only a write proven by async context to come from inside a transaction that rolled back is rejected with `P2028`, so another writer's rollback no longer rejects or discards unrelated work, including on Prisma 7, where a root statement shares the transaction's connection. A write whose callback lost its async context through an external `AsyncResource` runs after the rollback and persists: use the passed transaction client for transactional writes. Native SQLite adapters serialize root writes and both transaction forms before Prisma starts them, keeping driver acquisition waits outside the connection pool, and transactions opened on the same client take a turn in that queue. Batched enqueues retain batch semantics without gaining an interactive timeout. Expired native transaction callbacks release the queue even when the callback never settles, and the rejection now says the timeout passed. On Prisma 7, a call to a root port inside a raw `client.$transaction(fn)` used to commit with that transaction by accident of the shared connection; it now fails with `P2028` after 5 s while the adapter write persists alone, so build ports over `tx`. A raw `$transaction` on the root client inside a transaction's callback waits for the outer transaction's deadline and then commits on its own: never start one there. On SQLite on Prisma 6 and 7, `maxWait` does not bound the time a raw transaction waits in the queue; everything ahead of it has a deadline. `enqueue` and `enqueueParallel` on a Prisma 7 SQLite transaction client now throw "does not support $transaction" at once, as on Prisma 6, instead of queueing behind their own transaction.

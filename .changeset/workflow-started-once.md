A run's start now writes one `workflow:started` whichever of `run.claimPending` and `run.transition` moves it from `PENDING` to `RUNNING` first. A `run.transition` dispatched for a pending run that no host had claimed yet created the first group's stage records, queued their jobs and wrote `workflow:started`, but left the run `PENDING`: a job of that group was turned away as a ghost (`ghostReason: "race"`) until the claim, and the claim then wrote a second `workflow:started` and queued the jobs again. The transition now sets the run `RUNNING` (with `startedAt`) in the same version-guarded write that claims it, so a later `run.claimPending` finds nothing to claim, and a run that is not `PENDING` and has no stage rows is given its first group without a start event. A run whose first group is empty stays `PENDING` for the claim, which fails it with `EMPTY_STAGE_GRAPH`. The statements of both handlers are unchanged: the transition's existing claim write also sets the status. A redrive still writes one `workflow:started`. A run that an earlier release started with a transition and left `PENDING` is claimed as before and still shows two; the console reads that pair as one start. No port or schema changes.

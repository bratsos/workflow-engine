A dead-lettered outbox event can no longer be lost to a crash. `outbox.flush` stamps `publishedAt` when it claims an event and, on the last allowed failure, moved the event to the DLQ and then released the claim in a second write. A process that died between the two left `dlqAt` and `publishedAt` both set, and `plugin.replayDLQ` cleared only `dlqAt`: the event then read as published and was never delivered (reproduced through `outbox.flush`, an injected crash, `plugin.replayDLQ` and `outbox.flush` on Prisma 7 SQLite: the replay reported 1 event and the next flush published 0). `moveOutboxEventToDLQ` now sets `dlqAt` and clears `publishedAt` in one write, and `replayDLQEvents` clears any `publishedAt`, in the Prisma adapters (Prisma 6, 7 and 8, PostgreSQL and SQLite) and the in-memory adapter. Rows an earlier version left in that state count as dead-lettered in `engine.stats` and are revived by the next `plugin.replayDLQ`; `UPDATE outbox_events SET "publishedAt" = NULL WHERE "dlqAt" IS NOT NULL AND "publishedAt" IS NOT NULL` normalises them without a replay. This does not change the delivery guarantee, which the docs now state exactly (an earlier page promised at-least-once, which was never true): events are written in the transaction of the state change they describe (no phantom events); `outbox.flush` claims an event (stamps `publishedAt`) before it calls `emit`, so each claim gets one delivery attempt and two hosts never deliver the same event; a sink failure is retried up to the retry budget (`maxRetries`, default 3) and then dead-lettered; an event is lost only if the process dies between the claim and the emit (closing that window needs a claim state of its own, a schema change); the engine's own progress never depends on the sink; a consumer that needs every event reads the `outbox_events` table or the console. A custom `Persistence` must clear the stamp in the same write in `moveOutboxEventToDLQ` and in `replayDLQEvents`; `persistenceConformanceSuite` checks it.

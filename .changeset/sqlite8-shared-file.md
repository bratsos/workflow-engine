Prisma 8 SQLite: several root clients of one file in one process share one statement queue. Each root has its own synchronous connection, so a write on one root while another held the file's write lock waited inside the driver and blocked the event loop for the whole busy timeout (an engine `run.create` took 5.3 s; an outbox flush across 13 roots stalled the process). A root now waits its turn without blocking, and closes the other roots' open reads before it writes. A root leaves the file's registry when its client is closed, and the file's entry goes with its last root; a root opened later joins the queue of the roots still open. A queued write that waited behind another yields to the event loop before it runs, so a burst across roots no longer holds timers back until the queue drains; other roots' reads are held back only around each autocommit write and at a transaction's commit, so a transaction's callback can read through another root; and a raw transaction left open on any root of the file makes engine writes on every root wait for it, for at most 5 s. An uncontended write does not yield, so single-root throughput is unchanged (median CPU for 300 sequential `run.create` calls, 8 samples each: 987 ms against 1,085 ms on alpha.20 with a rollback journal, 744 ms against 728 ms in WAL).

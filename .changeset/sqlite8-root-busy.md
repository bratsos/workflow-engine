Prisma 8 SQLite: a root statement that fails with a busy error no longer makes later root writes vanish. `node:sqlite` does not reset a statement whose first step fails `SQLITE_BUSY`, and the Prisma 8 driver iterates every statement that returns rows, so SQLite kept the statement active on the shared root connection; after a statement that writes, every later root write reported success, was not committed, and was rolled back when the statement object was collected. `fromPrisma8` now classifies each root statement once: one that is not provably a read (`SELECT`, `VALUES`, `EXPLAIN`, `WITH` ending in `SELECT` or `VALUES`) waits in the root write queue, and only its turn runs it, under `BEGIN IMMEDIATE` when it returns rows, through the driver's `execute` when it returns none, and as it is for a `PRAGMA` that returns rows. No transaction can be opened on the root connection outside that queue. Raw `VALUES` reads no longer wait in the queue, and a raw `EXPLAIN ... RETURNING` returns the plan. A root read that fails busy at its first step remains a limit of the driver: it stays active until it is garbage collected, which blocks other connections' commits (rollback journal) or pins a stale snapshot (WAL), and loses no write.

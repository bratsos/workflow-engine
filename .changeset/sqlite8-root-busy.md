Prisma 8 SQLite: a root statement that failed with a busy error no longer leaves the root connection unusable. `node:sqlite` does not reset a statement whose first step fails `SQLITE_BUSY`, and the Prisma 8 driver iterates every statement that returns rows, so SQLite kept the statement active. After a write that returns rows (`create`, `update`, `upsert`, `delete`, raw `... RETURNING`) every later root write reported success but was not committed, and was rolled back when the statement object was collected. `fromPrisma8` now takes the write lock with `BEGIN IMMEDIATE` before such a statement and commits after it. After a read, the next statement kept a read transaction open (other connections could not commit on a rollback journal; in WAL the root read a stale snapshot, failed writes with `SQLITE_BUSY_SNAPSHOT` and held back the checkpoint) until the statement was collected. `fromPrisma8` now runs the garbage collector a few times before it reports a busy error from a root read, which finalizes the statement. The decision to read SQLite integers as text now comes from the statement's plan, not from which executor runs it.

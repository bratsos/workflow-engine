The SQLite adapters refuse a file that another Prisma major wrote. Prisma 6 stores `DateTime` as integer epoch milliseconds in SQLite, Prisma 7 and 8 as ISO text, and SQLite orders every integer before every text value, so across majors every date comparison is decided by the type: a Prisma 7 client on a Prisma 6 file offered a run completed a moment ago to `run.purge` and a run updated a moment ago to `run.reapStuck` (and the reverse never polled a stage whose deadline had passed). `PrismaWorkflowPersistence`, `PrismaJobQueue`, `PrismaStepLedger` and `PrismaAICallLogger` on SQLite now check before every method, in one statement through the client's tagged `$queryRaw`, or `$queryRawUnsafe` when that is all the client has: the oldest and newest stored value of every date column an index leads with (`workflow_runs.createdAt`, `outbox_events.publishedAt` and `dlqAt`, `workflow_stages.nextPollAt`, `job_queue.nextPollAt`), the date of one row of each table whose rows no run implies (`job_queue.createdAt`, `outbox_events.occurredAt`, `idempotency_keys.createdAt`, `ai_calls.createdAt`), and a `Date` as the client binds it, read off the client and not from a table of majors (ten index lookups, four one-row reads and one index seek per stored day in each indexed column: a median 0.02 ms with 100,000 runs and events on one day, 0.36 ms over 365 days). It compares the storage class and, when both are text, the form (the text with every digit replaced, which tells Prisma 7's `+00:00` from Prisma 8's `Z`, the path of an upgrade). A foreign class or form makes the method throw the new exported `SqliteDateStorageError` (`code: "SQLITE_DATE_STORAGE_MISMATCH"`, `kind` `"class"`, `"form"` or `"sqlite-timestamp"`, `column`, showing what is stored and what is bound and linking the docs) before it reads or writes anything. A refusal is not remembered: every later call checks again, so a file whose rows were rewritten is accepted without a restart. The check fails closed: when it cannot run (a database error, a missing table) the method throws the new exported `SqliteDateStorageUnverifiedError` (`code: "SQLITE_DATE_STORAGE_UNVERIFIED"`, `reason: "probe-failed"`, the database error as `cause`) and runs nothing, and the next call checks again; a pass is remembered for the client only when it saw a stored date and, on a Prisma 8 root, no transaction the consumer opened on the root connection was uncommitted while it ran. On a file with no stored date the method runs and the next call checks again: every table is either sampled or holds rows that belong to a run whose date is read, so no row exists that the call could compare. **Breaking:** a SQLite client with neither `$queryRaw` nor `$queryRawUnsafe` is refused on every call with `SqliteDateStorageUnverifiedError` (`reason: "no-raw-query"`, naming both); it used to run unchecked. Which methods are guarded is decided by name (every method except a short list of synchronous ones, and loading fails if none is wrapped), not by how the code was compiled, so a build that lowers `async` still guards every entry point; a transaction's clone is checked through its parent before the transaction opens. Checked on real files written by one major and opened by another, in all six directions, for each adapter, the console read port and both hosts, with the full client, a client with only one of the two raw reads and a client with neither, cold and with a process that had started on the empty file before the other major wrote. The prerequisite: one Prisma major per file, also while it is empty. Two majors that start on an empty file cannot be told apart until one of them writes; after that, the other refuses on its next call. Not detected: a foreign text form on rows strictly between the oldest and newest of a column, and the rows of a sampled table other than the one read; only a file an earlier release mixed, or two majors writing at once, can hold them. Follow the [SQLite major-switch procedure](https://workflow-engine.dev/persistence/prisma-setup#switching-sqlite-prisma-majors). Before purging runs and clearing the outbox, idempotency and AI tables, drain until no unpublished event or live claim remains and resolve or explicitly discard dead letters. Prisma 8 → 6 requires a fresh file.

New exported `assertSqliteDateStorage(prisma)` runs the same check for code that owns a client (the console read port uses it), and `JobTransport` and `JobQueue` gain an optional `verifyStorage(): Promise<void>` that the Node host calls at start and the serverless host calls before each entry point. The Prisma job queue implements it and `createSpillingJobTransport` forwards it. Nothing is required of a custom transport.

The guard treats SQLite INTEGER and REAL timestamps as one numeric form, including the better-sqlite3 adapter's `unixepoch-ms` mode. A numeric writer refuses a database with TEXT date affinity even after a drain. Calls sharing a pending probe wait for it to settle.

The guard also refuses SQLite's own timestamp form (`2026-11-18 06:30:09`, written by `CURRENT_TIMESTAMP`, `datetime('now')` and the `createdAt` column default of the Prisma 6 and 7 schemas when an insert leaves it out), which the engine compared wrongly by up to a day, with `kind: "sqlite-timestamp"` and a `recovery` property holding the `UPDATE` that rewrites the column in the client's form. It finds such a row anywhere in an indexed date column (one index seek per stored day) and as the oldest, newest or sampled value; it does not see one on a row of a sampled table other than the one it reads.

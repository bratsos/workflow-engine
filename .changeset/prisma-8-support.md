Prisma 8 support, next to 6 and 7, from one codebase and the same conformance suites.

- **`fromPrisma8(db)` makes a Prisma 8 client satisfy the adapters.** Wrap the client from `postgres({ contract, url })` once and pass the result wherever a Prisma client goes: `createPrismaWorkflowPersistence(fromPrisma8(db))`, and the same for the job queue, AI call logger, step ledger, blob store and `createPrismaConsoleReadPort`. It is exported from `@bratsos/workflow-engine` and `@bratsos/workflow-engine/persistence/prisma`, types `db` structurally and imports nothing from Prisma. Delegate calls are compiled to SQL from `db.contract`, with atomic `{ increment }`, lazy `$transaction([...])` batches, `isolationLevel`, Prisma's `P2025` for a missing row, Prisma's `P2028` when a `$transaction(fn)` outlives its `timeout` (5s by default), and an error for any argument shape that does not behave as on Prisma 6 and 7, including a required column given `undefined`. At the `timeout` the transaction rolls back and its connection is freed even if the callback never settles, and the caller is rejected with `P2028` there and then (on Prisma 6 and 7 the caller keeps waiting for the callback). A `createMany` too large for Postgres's 65,535 bind parameters is split into several statements inside one transaction, and `$transaction(fn, { isolationLevel })` also works as the first transaction on a fresh client. `Date` and array parameters in raw SQL are converted for you. Inside your own transaction, build the ports over its `tx` with `fromPrisma8(tx, { contract: db.contract })`: your `tx.orm` writes and the engine's commit or roll back together.
- **Prisma 8 is a release candidate.** Support is tested against exactly `prisma@8.0.0-rc.29` with `@prisma/orm-postgres@8.0.0-rc.21`; pin both, because the `latest` pair crashed `prisma contract emit`. It needs Node 22.18+/24.11+/26+, TypeScript 5.9+ and PostgreSQL 15+. Prisma 7 stays the default path (Prisma 6 receives only security patches until 2026-11-19); the install, setup and adoption steps for all three majors are in the Prisma Setup docs. An existing Prisma 6 or 7 database moves to Prisma 8 with `prisma db sign`: its tables do not change.
- **Your contract must carry the engine's tables.** `prisma/contract.prisma` ships in the package as the reference: timestamps are `TimestampString(3)` and `Status` is a native enum, which `fromPrisma8` checks at construction, naming the fix. `prisma/mixed-order-indexes.sql` gives the five indexes their descending order, which a contract cannot express. Prisma 8 is Postgres-only here: `databaseType: "sqlite"` over a `fromPrisma8` client throws.
- **The console reads on Prisma 8 too.** Prisma 8 drops the columns a raw read does not declare, so every console query now declares its columns; Prisma 6 and 7 are unaffected. A reader you wrap around a client of your own must forward `$withColumns` from it, and a raw read of your own through `fromPrisma8` runs on `client.$withColumns(...)`; the error says so. `workflow-console --database-url` needs `@prisma/client`, so on Prisma 8 use `--config` with a module that builds the reader with `fromPrisma8`; the error says so.
- **`npx workflow-console` runs when installed from npm.** The bin is a symlink in `node_modules/.bin`, and the entry check compared it with the real file, so the command exited 0 without doing anything on every Prisma major. `--config` is the only console route on Prisma 8.
- **The shipped `prisma/schema.prisma` no longer has `url = env("DATABASE_URL")`.** Prisma 7 rejects the line (P1012), so the file now matches Prisma 7; the previous alpha's file was the other way round. A Prisma 6 project that copies the file adds the line back to the `datasource` block, as Prisma Setup shows; Prisma 7 sets the URL in `prisma.config.ts`. The tables, columns and indexes are unchanged, so no database change is needed.

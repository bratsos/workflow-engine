# @bratsos/workflow-engine-console

## 1.0.0-alpha.0

### Minor Changes

- a22204a: Durable steps, injected AI services, one AI primitive with a realtime/batch policy, a builder-first typed workflow API, definition versioning, an embeddable operational console, and the 1.0 removals.

  **Breaking (major):**

  - Removed the APIs deprecated for 1.0: `ModelStatsTracker`, `getModelById`, `ModelWithRecorder`, `printAvailableModels`, `getRegisteredModel`, `listRegisteredModels`, `getDefaultModel`, `modelSupportsBatch`, the positional `recordCall(modelKey, prompt, response, tokens, options)` overload (the object form stays), `requireStageOutput`, and `apiKey` on the suspended state schema. Check batch capability with `getModel(key).supportsAsyncBatch`; configure models with `registerModels()`.
  - `defineWorkflow` no longer takes an `output` option. The workflow output schema is always the last stage's output schema (or the merged object of the last parallel group).
  - `StageContext` and `CheckCompletionContext` gained `step`, `ai` and `aiLogger`, all **required** — `StageContext.step` is no longer optional, and `CheckCompletionContext` now carries a `step` scoped to the same stage record. Hand-built contexts (custom hosts, tests that construct a context by hand) must provide them; `createStepApi()` from `@bratsos/workflow-engine/kernel` builds a ledger-less step API that throws `StepLedgerNotConfiguredError`.
  - `StageContext` gained `abortSignal: AbortSignal`, **required**, and `StepRunContext` gained the same signal. A hand-built context must provide one (`new AbortController().signal` for a context that never aborts); every kernel path and host-remote's activity worker build it.
  - `ctx.log` and `ctx.onLog` are typed as returning `void`. Code that awaited them still compiles; the type no longer suggests it.
  - `AIStreamResult.rawResult` is `undefined` when the stream came from an adapter.
  - `ModelKey` is open in both forms. The _type_ accepts any string, and the exported _zod schema_ is now `z.string().min(1)` instead of a registry refinement — a `schemas.config` field typed with it no longer rejects an unregistered key at `run.create` with "Model not found". Validation stays at `getModel()`.
  - `WorkflowBuilder.stage(prebuilt)` and `.pipe(prebuilt)` now check the stage's declared context against the accumulated one. A stage that requires a key no earlier stage produces (or produces with an incompatible type) no longer compiles; the parameter resolves to `{ __error: "stage requires context keys not produced by earlier stages: ..." }`. Stages built without an explicit context are unaffected.
  - The Prisma schema gains a `WorkflowStep` model (`attempt`, `leaseExpiresAt`, `deadlineAt`, `externalKey` included) used by `PrismaStepLedger`; consumers using durable steps need a migration.
  - `ctx.step.run(id, fn)` calls `fn` with a `StepRunContext` argument (`{ stepId, externalKey, attempt, isReclaim }`). Existing zero-argument bodies are unaffected; a body typed as `() => Promise<T>` still satisfies the parameter.

  **New features:**

  - **Durable steps.** `ctx.step.run(id, fn, { lease, retries, retryDelay })` (`lease` and `retryDelay` take milliseconds or a duration string; `leaseMs` and `retryDelayMs` still work as deprecated aliases, and the canonical name wins when both are given), `ctx.step.waitFor(id, { poll, ready, every, timeout, pollBackoffMs })`, `ctx.step.waitForSignal(id, { timeout, keepalive })` and `ctx.step.sleep(id, duration)` record side effects in a `StepLedger` (`InMemoryStepLedger`, `PrismaStepLedger`); a suspended stage resumes by replaying `execute()` with completed steps answered from the ledger. A `step.signal` kernel command completes a signal wait and is idempotent. Leases re-claim steps left `running` by a dead worker, `retries` re-run a thrown step, wait deadlines are stored once and never slide (`StepTimeoutError` on expiry), a throwing `poll` backs off instead of failing the stage, replay saves artifacts, and re-running a stage from scratch starts its steps over (which rows survive that is set out below). Control-flow errors are branded (`isStepControlFlowError`) and a stage body that swallows one still suspends.
  - **`ctx.step.ai`.** `generateText` and `generateObject` are memoized through the ledger. `map(id, items, spec)` runs one prompt per item under `policy: "auto" | "realtime" | "batch"` with the same schema validation and repair on both paths, an in-process concurrency limit, a call budget (`AiMapBudgetExceededError`), a stored batch deadline, and `onExpiry: "fail" | "partial"` (`AiMapBatchFailedError`). All batch bookkeeping lives in step results.
  - **`ctx.ai` and `ctx.aiLogger`.** `createKernel({ services: { aiLogger, ai? } })` provides a lazily built `AIHelper` on every stage and `checkCompletion` context under the topic `workflow.<runId>.stage.<stageId>`, with call logs in the run's log table. `createMockAIHelperFactory()` in `@bratsos/workflow-engine/testing` provides the mock for tests. Accessing `ctx.ai` without services throws `AIServicesNotConfiguredError`.
  - **Adapter seam.** `AIHelperOptions.adapter: AIAdapter` swaps the transport for any subset of `generateText`, `generateObject`, `embed` and `streamText` below logging and cost; child helpers inherit it. Adapter responses may carry `costUsd`, recorded as the reported cost.
  - **Timeouts.** `AIHelperOptions.timeout.perCallMs` and per-call `timeoutMs` on text, object, embed and stream options; expiry throws `AICallTimeoutError` and still logs the failure row.
  - **Builder-first workflows.** `defineWorkflow(id, { input }).stage(id, definition)` infers the context from earlier stages so `ctx.require()` is typed and `dependencies` only accepts earlier ids; `.stage(prebuilt)`, `.pipe()`, `.parallel([...])` and `.parallel((group) => ...)` carry the same inference; `InferWorkflowContext`, `InferWorkflowInput`, `InferWorkflowOutput`, `InferWorkflowStageIds` and `InferStageOutputById` expose the inferred types.
  - The package now ships `prisma/schema.prisma`, and the Prisma adapters no longer import `@prisma/client` (Prisma 7's generator has no fixed client path).
  - **Durable steps under `Promise.all`.** When one of several concurrent steps suspends, the stage factory now lets every in-flight `run` finish and record — bounded by the longest remaining lease — before the suspension is persisted, so the replay finds completed rows instead of meeting `StepInFlight` until the leases expire.
  - **Lease heartbeat.** `StepRunContext.heartbeat()` extends a running `run` step's lease by its `lease` from now, under a compare-and-set on `{ status: "running", attempt }` so an execution whose row was already taken over cannot revive it — it rejects with the new `StepLeaseLostError` (exported from the root) instead. `StepRunOptions.heartbeat: number | string | false` (default `false`) does the same automatically on that interval while the body is pending, with the timer `unref`'d and cleared when the body settles. The suspension bookkeeping under `Promise.all` waits under the extended lease.
  - **Retry backoff.** `StepRunOptions.retryBackoff: { factor?, maxDelay?, jitter? }` grows `retryDelay` per failed attempt (`retryDelay * factor^(n-1)`, capped at `maxDelay`, optionally full-jittered) and reads the attempt off the step row so a retry replayed by another process computes the same delay; `createStepApi({ random })` injects the jitter source. The default factor of 1 keeps the fixed delay.
  - **Signal-wait keepalive.** A `waitForSignal` step re-suspends every `keepalive` (`StepSignalOptions.keepalive`, milliseconds or a duration string, default five minutes, bounded by `timeout`) while no signal has arrived, instead of every 30 seconds. Signal latency is unchanged — `step.signal` resets the stage's `nextPollAt` to now, so a landed signal wakes the stage on the next host tick — the keepalive only bounds how long a lost nudge can delay the wake, so a stage waiting days for a human no longer replays its body every half minute.
  - **Step options on single AI calls.** `ctx.step.ai.generateText(id, model, prompt, options?, stepOptions?)` and `generateObject(..., schema, options?, stepOptions?)` forward a `StepRunOptions` (`retries`, `retryDelay`, `lease`) to the underlying `step.run`, so one model call retries durably like any other step.
  - **`ctx.step.ai.streamText(id, model, prompt, options?, stepOptions?)`.** Streams through `ctx.ai.streamText` on the first execution (forwarding `onChunk`) and stores the final text, tokens, cost and reasoning as one `run` step; a replay returns the stored `StepStreamResult` without contacting the model and calls `onChunk` once with the whole text. For hosts that kill an idle non-streaming connection.
  - **`ctx.step.ai.map` additions.** A failed item carries `errorName` (the `Error.name` of the last failure, memoized so it survives replays; never a `cause` — results must stay JSON). `realtime.minDelayMs` paces each concurrency slot, replacing hand-written cooldowns. `stream: true` sends realtime items through `ctx.ai.streamText`, with `schema` still validating the collected text.
  - **Test harness.** `createTestHarness({ workflows, services?, clock?, stepLedger?, ... })` in `@bratsos/workflow-engine/testing` returns the kernel, every in-memory port, the step ledger, the AI logger, the mock AI factory and the fake clock, plus `run(workflowId, input, config?)` (drives claim → execute → poll suspended → flush → advance until the run is terminal) and `tick()` (one round, returning a `TickReport`). `start(workflowId, input, config?)` creates a run without driving it and `tickUntil(predicate, { maxTicks? })` ticks until a condition holds, so a test can wait for one named step's result and assert part-way through a run rather than only at the end. `createTestKernel` is exported from the same entry.
  - **Mocking a durable step's outcome.** `harness.steps` decides what a durable step does before a run and reads back what the ledger recorded: `mockResult(stepId, result)`, `mockError(stepId, error, { attempt? })`, `mockTimeout(stepId)` (`waitFor` and `waitForSignal` only — they are the kinds that have a deadline, and mocking any other kind this way throws), `skipSleep(stepId)`, `skipSleeps()` and `clearMocks()`, with `record`, `records`, `status`, `result`, `error` and `wasMocked` to assert on. A mocked step is a pre-seeded ledger row rather than an interception layer: the engine already short-circuits a `completed` row, rethrows a `failed` one and times out a wait whose deadline has passed, so a seed only writes the row the engine was about to write, and it is applied as a patch on the record the engine passed to `claim()`, so `stageRecordId`, `stepId`, `seq`, `kind` and `externalKey` stay the engine's own values and a mock can never disagree with the engine about what step it is. Three consequences are documented in the API itself and in the testing reference: seeds match by step id across stages, so a step id two stages deliberately share is answered for whichever claims it first; a seed answers for the whole run, and is re-asserted when the engine reopens a failed stage's step rows rather than letting the real body run part-way through; and `mockError` records at `MOCKED_FAILURE_ATTEMPT`, above any `retries` budget a step could declare, so a mocked failure is the step's final answer unless you seed a lower `attempt` to test the retry path. `createMockStepLedger(inner, clock)` is exported for use without the harness; it mirrors the `StepLedger` port exactly, including whether the wrapped ledger implements the optional `clearExcept`, and a test enumerates the port's whole surface so adding a method to `StepLedger` fails to compile until the wrapper forwards it.
  - **`stepLedgerConformanceSuite`**, exported from `@bratsos/workflow-engine/testing` alongside the persistence, job-queue and AI-logger suites and taking the same `ConformanceTestApi` third argument. `StepLedger` was the only port with no shared suite, which is why the `result` divergence described under _Step ledger integrity_ below survived a release: `clearExcept`, `compareAndSet` with and without a pinned attempt, and result nulling were all exercised against the in-memory fake alone. It takes a `StepLedgerFixture` (`StepLedger & { reset?: () => Promise<void> }`) rather than the `ResettableFixture` the other suites take, because `StepLedger` has a `clear(stageRecordId)` of its own that the shared fixture's argument-less `clear()` would collide with. It runs against `InMemoryStepLedger`, and against `PrismaStepLedger` in this repository's own Postgres run.
  - **`runToCompletion`: a supported synchronous drain loop.** New export from `@bratsos/workflow-engine-host-serverless`. `runToCompletion({ kernel, jobTransport, persistence, command })` creates a run and drives it to a terminal state inside the calling request — the loop every caller wanting near-synchronous behaviour was writing by hand — and returns `{ workflowRunId, status, outcome, output?, reason?, jobsProcessed, foreignJobsProcessed, suspendedStageId? }`. Its three limits are in the API's own documentation rather than a footnote. It shares the queue, so it can execute another caller's job; `foreignJobsProcessed` reports how much of that happened, and giving it its own `jobTransport` is the answer when that is unacceptable. It cannot finish a workflow that suspends, and returns `outcome: "suspended"` naming the stage instead of spinning. And it is bounded by `maxJobs` (default 50) and `maxClaimRounds` (default 5), returning `outcome: "incomplete"` with a `reason` when either runs out, so it never throws for a non-terminal run and never loops unbounded. It deliberately does not poll suspended stages or reap leases — that is `runMaintenanceTick()`, and doing it here is what would make it spin.
  - **`workflow_engine_enqueue`: transactional enqueue from SQL.** New `sql/enqueue.sql`, shipped in the package and applied by your own migration rather than created at runtime, so a database trigger or a service that is not TypeScript can create a workflow run inside its own transaction: `PERFORM workflow_engine_enqueue('order:' || v_order_id, 'fulfil-order', 'Fulfil Order', jsonb_build_object('orderId', v_order_id))`. It writes exactly the rows `run.create` writes, in the same order — the idempotency key, the run, the `workflow:created` outbox event — and leaves the run `PENDING` for `run.claimPending`; replaying an idempotency key returns the same run id. Three things it cannot do, each written down in the file and in the persistence reference: it cannot validate input against the workflow's Zod schema, so bad input fails at the first stage instead of at enqueue; it cannot compute the definition version, so it creates the run **unpinned** by default and refuses a `p_definition_version` whose `workflow_definitions` row does not exist, because pinning a run to an unregistered version would strand it; and it stores `p_config` verbatim rather than merging stage defaults, which changes only what the column shows a reader, because every stage re-parses its config slice through its own schema when it executes. Requires PostgreSQL 13+. `sql-enqueue.test.ts` (gated on `DATABASE_URL`, part of `pnpm test:pg`) creates one run each way and asserts the two `workflow_runs` rows, the two `idempotency_keys` results and the two outbox events agree column by column, and that both execute to the same output — that test is what stops the two paths drifting.
  - **Mock AI scripting.** `createMockAIHelperFactory({ helper })` hands out the caller's instance, and `createAtTopic`/`createChild` construct through `this.constructor`, so a `MockAIHelper` subclass survives. `failOnce(match, error?)` arms a one-shot failure (substring, RegExp, or a predicate over `{ modelKey, prompt, kind }`), and `mockObjectResponseForSchema(schema, value)` dispatches object responses on Zod schema identity.
  - **Host helper ergonomics.** Every field of `RunMaintenanceTickOptions`, and every field of `ExecuteJobWithHeartbeatOptions` other than `jobTransport` and `job`, is optional, with `HOST_DEFAULTS` (which now also carries `workerId` and `logPrefix`) applied inside. `runMaintenanceTick(kernel)` and `executeJobWithHeartbeat(kernel, { jobTransport, job })` work as-is.
  - **Export surface.** `WorkflowRegistry` is exported from the root entry alongside `Workflow`, and `TextInput`, `ContentPart`, `TextPart`, `MediaPart` and `StreamTextInput` are exported from both the root and `/client`, so every type in a public method signature is importable.
  - Reference `skills/workflow-engine/references/12-durable-steps.md` documents all of the above and the migration from `defineAsyncBatchStage` to steps. `skills/workflow-engine/migrations/migrate-0.13-to-1.0.md` is the upgrade guide: a column-level database checklist with SQL (the `workflow_steps` table, `ai_calls.batchId`/`requestId`, and the columns every dispatch writes), the API removals with replacements, the builder and `defineAsyncBatchStage` → `ctx.step.ai.map` migrations, `createKernel({ services, stepLedger })`, the AI SDK 7 peer ranges and the behaviour changes.
  - The agent skill covers the rest of this release. `skills/workflow-engine/references/` gains `13-definition-versioning.md` (the derived structural hash, `.version()`, the `workflow_definitions` snapshot, version-filtered claiming through `serves`, `ghostReason: "version"`, `run.listVersions`, the `PersistenceCore` additions, and shadowing with `shadowVersions` / `shadowRuns` / `assertShadowCompatible`), `14-redrive.md` (`run.redrive`'s `lastFailure` / `start` / `stage` modes, re-pinning with `definitionVersion: "latest"`, the preserved `run.supersededAttempt` annotation, and migrating off the deprecated `run.rerunFrom`), `15-large-payloads.md` (the claim check: automatic step-result spilling at 64 KiB, opt-in job-payload spilling through `createSpillingJobTransport`, `spillThresholdBytes`, and what is deliberately not spilled) and `16-operational-console.md` (`@bratsos/workflow-engine-console`). `03-runtime-setup.md` gains the degraded event sink and `spillThresholdBytes`; `05-persistence-setup.md`'s `PersistenceCore` listing gains the four definition-versioning methods, `claimNextPendingRun`'s `serves` and `workflow_engine_enqueue`; `07-testing-patterns.md` gains the step mocks; and `08-common-patterns.md`, `09-troubleshooting.md`, `10-annotations.md` and `12-durable-steps.md` are updated for redrive, `ghostReason: "version"`, the engine-written annotations and `StepLedger.clearExcept`.
  - The positioning is narrower and checkable. The docs-site introduction and both READMEs now state what the engine does in terms a reader can verify against the source, name the projects that ship the same design where they do, and list what the engine does not do — no arbitrary DAG, no child workflows, no per-tenant concurrency or throttle or rate limit, and exactly-once _recording_ of a step against at-least-once _execution_ of its body, which is the same boundary Inngest, Cloudflare Workflows, Hatchet, Restate and DBOS all document. The model-registry page no longer says OpenRouter's `max_price` "guarantees predictable AI spending": it says what the guard actually bounds, which is the per-token price of a routed call, not spend, and not the non-token charges OpenRouter documents as uncovered.

  **Fixes from the first real-world runs of 1.0.0-alpha.0:**

  - `AIAdapter.generateObject` results were read from `output` instead of `object`, so every adapter-based `generateObject` (and every `ctx.step.ai.map` item with a schema) returned `undefined`, logged an empty response and crashed. The object is resolved once from the adapter response; `generateText` reads the adapter's structured `object` the same way. The adapter seam is now covered end to end through the kernel (a real `createAIHelper` over a fake adapter across `generateText`, `generateObject`, `streamText`, `map` realtime and `map` with repair).
  - `ctx.step.ai.map` repair now engages for any error that carries the model's raw text (`text` or `cause.text`), a `ZodError` or a JSON `SyntaxError`, not only the AI SDK's `AI_NoObjectGeneratedError`; `NoObjectGeneratedError` is re-exported from the root entry so adapters can throw it. Realtime item retries (`realtime.retries`) run **in-process** — wait `retryDelayMs`, bump the ledger row's `attempt`, call again — instead of suspending and replaying the whole stage. `ctx.step.run` retries still suspend the stage.
  - The step seq ordinal is stable across replays of a stage that runs a map: item seqs are reserved in item order before any ledger lookup resolves, so a slow ledger cannot permute them and a `step.run` after the map is no longer reported as "non-deterministic step order".
  - `NodeHost.stop()` waits (bounded by `shutdownTimeoutMs`, default 10s) for the job in flight and then runs a final `outbox.flush`, so `workflow:completed` for a run finished by that process is published before it exits instead of by whichever process ticks next; `flushOutboxOnStop: false` opts out. The serverless host, which has no lifecycle, flushes after each `handleJob` (`flushOutboxAfterJob`, default true, bounded by `outboxFlushTimeoutMs`). The remote package is an activity worker with no outbox and is unchanged.
  - A stage failure with job attempts left is no longer recorded as `FAILED`: `job.execute` takes the job's `attempt`/`maxAttempts` (both hosts and the test harness pass them), leaves the stage `PENDING` with the error on `errorMessage`, keeps its ledger rows, and returns `willRetry: true`; the host re-enqueues through `jobTransport.fail(jobId, error, true)`, whose contract now states the transport must re-queue with backoff. With no attempts left the stage is `FAILED` and `run.transition` runs immediately on every host — previously a serverless consumer whose transport acknowledged without re-enqueueing saw a `FAILED` stage under a `RUNNING` run until `run.reapStuck`. The `maxRetries` field of the config presets is not read by the kernel; the transport's `maxAttempts` is the retry budget.
  - Google batch structured outputs send the full JSON Schema again. `@ai-sdk/google` (checked through 4.0.63) can only express a response schema as Gemini's OpenAPI-style `responseSchema`, which flattens nested discriminated unions, so on 1.0.0-alpha.0 every item of such a batch failed validation and was re-run realtime by repair (2x calls, discount lost). The engine now substitutes `generationConfig.responseJsonSchema` — what 0.13 sent through `@google/genai` — into the inline batch body per request key at the `fetch` boundary (`resolveAiSdkBatchModel` accepts `apiKey`/`baseURL`/`fetch` from `BatchOptions` for every vendor now). A batch too large to inline is uploaded as a file and keeps the provider's schema, with a WARN. The realtime `generateObject` path used `Output.object` in 0.13 as well and is unchanged. `getResults` logs a WARN naming the batch id and the first issue when more than half of a batch fails schema validation, and batch accounting rows now store the item prompt and `metadata.durationMs` (the batch wall time) like realtime rows.

  **Fixes from the second consumer trial:**

  - The stage wrapper no longer dereferences `ctx.step` when a hand-built context (custom host, a unit test calling `stage.execute(ctx)` directly) has none; the type stays required, every runtime probe is optional-chained.
  - `createPrismaWorkflowPersistence(prisma, { statusEnumName })` names the Prisma enum the Postgres claim statement casts with (default `"Status"`; the cast dates from 0.11). The statement is issued through `$queryRawUnsafe` with positional parameters when the client has it; `$queryRaw` stays the fallback for the default name. Both the persistence and `createPrismaJobQueue` take a `now` clock and bind that JS `Date` instead of `NOW()`, so raw-SQL timestamps are UTC like every Prisma write and follow an injected clock; `claimNextPendingRun({ now })` receives the kernel clock.
  - Batch provider resolution: the call's `batch.provider` first, then the model's new registry field `batchProvider` (`"openrouter" | "google" | "anthropic" | "openai"`), then the slug's native vendor, then OpenRouter. A model that names `batchProvider: "openrouter"` is batched there even without a catalog `:batch` row. When the vendor SDK is not installed (`@ai-sdk/anthropic` / `@ai-sdk/openai` are optional peers) and OpenRouter can batch the model, the helper falls back to the OpenRouter transport with a WARN instead of failing the submit with `Package "@ai-sdk/anthropic" is required`. Sync-generated entries (all `provider: "openrouter"`) keep resolving to their native vendor by default, as before. The OpenRouter batch client was verified live: the documented body shape is what the engine sends; a creation error `does not have a :batch endpoint` (the catalog row exists but the endpoint is not live for that model) is now explained in the error.
  - `MockTextResponse.output` seeds structured output for `generateText` + `Output.object(...)`; when omitted, the scripted `text` is parsed and validated through the output spec exactly as the AI SDK does (rejecting with `NoObjectGeneratedError`). The mock's `streamText` is unchanged: the real `streamText` has no `output` option.
  - `WorkflowRun.totalCost` / `totalTokens` are written on completion from `services.aiLogger.getStats("workflow.<runId>")` (falling back to the stages' `metrics` sum without services), and carried on `workflow:completed`. The 04-ai-integration paragraph now describes what the kernel does.
  - A completed job retry clears the stage's stale `errorMessage` (`UpdateStageInput.errorMessage` accepts `null`). `WorkflowStage.attempt` keeps counting `run.rerunFrom` reruns; job retries are counted on the `job_queue` row, which the reference now states.
  - A job retry of a thrown stage keeps its ledger rows and replays them (a consequence of recording retryable failures as `PENDING`): a map of N items followed by a throw costs no extra model calls on the retry. Only a `run.redrive` from `start`, and the stages after the one a redrive resumes, clear a stage's ledger outright, because their rows are keyed by a stage record the redrive deletes; a resumed stage keeps its ledger (see “`run.redrive` keeps the resumed stage's progress” below), and executing a stage whose attempts were exhausted clears every row except those naming an external effect, which are re-opened instead — see “Re-running a terminally failed stage keeps a live batch handle” below.
  - `createPrismaStepLedger` is exported from the root entry (a test now pins it, alongside the other `createPrisma*` helpers and `NoObjectGeneratedError`).
  - `generateObject` and `generateText` + `Output.object` now send identical requests: the one difference was the default temperature (`0` for `generateObject`, `0.7` for `generateText`). Neither sends a default any more — see the fourth-round entry below. This was the difference behind the consumer's "generateObject is less reliable than generateText + Output.object on the same model" — same messages, same JSON response format, different sampling.
  - The persistence reference lists every delegate `EnginePrismaClient` requires and states that a wall of `PrismaClient is not assignable to EnginePrismaClient` errors means one of them is missing (after 1.0, almost always `workflowStep`).

  **Fixes from the third consumer trial (kernel inside one Prisma transaction per tick):**

  - `PrismaStepLedger.claim` and `acquireIdempotencyKey` no longer rely on a caught unique violation on Postgres — a failed statement aborts a consumer's enclosing transaction (`25P02`) on every replay that re-claims completed steps. Both insert through `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`) and read the row back; "existing records win conflicts without throwing" now holds inside a transaction. `createPrismaStepLedger(prisma, { databaseType: "sqlite" })` keeps the create-and-catch path where `skipDuplicates` does not exist.
  - `createPrismaBlobStore(prisma)` / `PrismaBlobStore`, backed by an optional `WorkflowBlob` model (`workflow_blobs`, in `prisma/schema.prisma`), so a Prisma deployment has a blob store shared by every process without object storage; it requires only the `workflowBlob` delegate (`BlobPrismaClient`), not a change to `EnginePrismaClient`. A replay whose blob store lacks a completed stage's output now fails naming the blob key and the shared-store requirement instead of "missing the output of execution group N". The reference documents that the blob store must be shared by every process that executes or polls a run.
  - Raw SQL timestamps: `claimNextPendingRun` and the Postgres `dequeue` bind a JS `Date` from the configured clock (`now` option; the kernel passes its clock to the claim) instead of `NOW()`, which wrote session-local time into naive `TIMESTAMP(3)` columns while Prisma wrote UTC.
  - `ctx.step.waitFor` narrows through a type-guard `ready` (`(v): v is Done => ...` returns `Done`); the boolean form is unchanged.
  - Replays no longer re-emit `stage:suspended` / `workflow:suspended` on every poll while the stage is still waiting on the same step with the same deadline; the events are emitted when the wait starts and when the stage moves to a different wait (a run polled every ~8s for 5 minutes emitted 73 pairs on alpha.0).
  - Hosts treat a job whose run, workflow or stage no longer exists as a dead job: `executeJobWithHeartbeat` logs it, fails and acknowledges it, and returns `{ outcome: "failed", dead: true }` instead of throwing — an orphan `job_queue` row no longer aborts a serverless tick (or a transaction-per-tick consumer's whole tick).
  - OpenRouter's "No endpoints found that can handle the requested parameters" is wrapped with what to change: it is the outcome of the default `routing.requireParameters: true` excluding endpoints that ignore a requested parameter (typically `maxTokens`); the error names `routing: { requireParameters: false }`. The default stays `true` (chosen in 0.13 so a request's parameters are honoured rather than silently dropped).
  - Reference fix: `eventSink` is `{ emit }`, not `{ publish }`.
  - The one "OpenRouter API key is missing" on a replayed retry could not be reproduced: the realtime path uses the provider package's default `openrouter` instance, which reads `OPENROUTER_API_KEY` from `process.env` at call time (no caching in the engine), and the stage AI helper is built the same way on the job and poll paths; the only engine-side explanation is the variable being absent from that process's environment at that moment. Inject the key explicitly through a `providerResolver` in `services.ai` to remove the dependency on process environment.
  - `@bratsos/workflow-engine/testing` imports nothing from vitest, so it loads from a plain `tsx` script. The conformance suites take the test primitives as a third argument: `persistenceConformanceSuite(name, factory, { describe, it, expect, beforeEach })` (same for `aiCallLoggerConformanceSuite` and `jobQueueConformanceSuite`); `ConformanceTestApi` is exported. `check:bundle` now guards `dist/testing/index.js` against vitest (and the other forbidden peers) like it guards `client.js`.
  - The surfaces marked "removal at 1.0" are gone: `KernelConfig.scheduler` and `NoopScheduler`, `RunCreateCommand.metadata` (use `annotations`), the `ArtifactPersistence` methods and the eight legacy query methods on the `WorkflowPersistence` port, `enqueue` on the `JobQueue`/`JobTransport` ports (`enqueueParallel([job])`), and the `defineAsyncBatchStage` export from the root and `/client` entries (the async-batch mode itself still runs; `defineStage({ mode: "async-batch", checkCompletion })` is the internal equivalent). The built-in adapters keep the removed methods as plain class methods. `SuspendedStateSchema.submittedAt/pollInterval/maxWaitTime` stay, with a corrected note: `defineStage()` back-fills them for async-batch `checkCompletion`, so they go away with that mode, not on their own. `workflow-engine-codemod --from 0.13` (new) and `--from 0.11/0.12` flag `defineAsyncBatchStage`, `checkCompletion`, `requireStageOutput`, `experimental_output` and the removed model helpers with the guide pointer (rule 7).

  **Fixes from the batch-idempotency round (1.0.0-alpha.9) — a reclaimed submit created, and paid for, a second provider batch:**

  - **A durable `run` body that made a non-idempotent external call was executed twice after a worker crash.** The batch path made this expensive: `ctx.step.ai.map` submits through a `${id}:submit` step, and a worker that died between the provider accepting the batch and the ledger recording it left the row `running`; five minutes later the lease expired, the replay re-executed the body, and a second batch was created. The first was orphaned — still processed, still billed, never read, and absent from the run's cost accounting. Reproduced against a fake backend counting creations: **2 batches before the fix, 1 after.** Google documents the underlying behaviour ("if you send the same creation request twice, two separate batch jobs will be created"), and none of the four batch transports dedupes by content.

    The fix is general, because any `ctx.step.run` body making an external call has the same problem:

    - **Every `run` step carries a deterministic external key.** `deriveStepExternalKey(stageRecordId, stepId)` produces `wfe-<128-bit hash>` (36 characters of `[a-z0-9-]`, so it fits Anthropic's `custom_id` charset, OpenAI's 512-character metadata values and Gemini's `displayName`). It is written to the new `workflow_steps.externalKey` column **when the row is claimed, before the body runs**, so an operator can read it out of the database and search a provider for an orphaned effect without the process that made it.
    - **The body receives it.** `ctx.step.run(id, fn)` now calls `fn(step: StepRunContext)` with `{ stepId, externalKey, attempt, isReclaim }`. Pass `externalKey` to a provider that honours request idempotency, stamp it into provider-side metadata, or — when `isReclaim` is true — search for the effect before creating it. Bodies that ignore the argument are unchanged.
    - **Batch adapters stamp and search.** The OpenAI adapter puts the key in the batch's `metadata` (`POST /v1/batches` takes 16 key-value pairs; `GET /v1/batches` returns them) and the Google adapter overwrites the AI SDK's generated `batch.displayName` with it (`GET /v1beta/batches` lists it) — both at the `fetch` boundary, since neither provider SDK exposes a hook. A reclaimed submit adopts the batch carrying its key and keeps polling it; a partition the dead worker never reached is simply created, so a crash halfway through a fan-out costs nothing.
    - **Where recovery is impossible, the failure is loud.** Anthropic Message Batches carry no metadata field and OpenRouter's beta batch body takes only `endpoint`, `model` and `requests`; neither offers an idempotency header the engine can rely on. A reclaimed submit on those transports now throws `BatchNotAdoptableError` naming the transport and the external key, instead of silently creating and billing a second batch. **This is a behaviour change** — set `batch: { onReclaim: "resubmit" }` on the map to accept the duplicate cost and get the old behaviour.
    - **Any step can declare itself unsafe to re-execute.** `ctx.step.run(id, fn, { onReclaim: "fail" })` refuses the lease-expiry takeover and fails the step with `StepNotReplaySafeError`, naming the step, when its lease expired and its external key. The default is `"rerun"` — exactly what every earlier version did — so steps that are safe to retry are unaffected. `onReclaim` governs the lease-expiry takeover only, not `retries`: a body that _threw_ has said its effect did not take.

  - **Migration:** add the column to `workflow_steps`. `ALTER TABLE "workflow_steps" ADD COLUMN IF NOT EXISTS "externalKey" TEXT;` (nullable; rows written before alpha.9 read back as `null`). The 0.13 → 1.0 guide carries it in the table definition too.

  - **Checked, and found correct: the batch discount does not compound with a cache discount anywhere in the cost model.** Vertex documents that "the discounts for cache and batch don't stack; the 90% cache hit discount takes precedence over the batch discount", and the Gemini Developer API bills a `cached_content` hit at context-caching rates rather than batch rates — so a model that multiplied 50% by 90% would be wrong. `calculateBatchCost` applies exactly one adjustment to the base price (the vendor percentage on a native transport, or the absolute `":batch"` catalog price on OpenRouter), never both, and the engine models no cached-token bucket and has no Vertex transport, so there is nothing to compound. No number changed; a test now pins the single-adjustment property so a later cache-aware price cannot quietly stack, and 06-async-batch-stages.md states the caveat — on a Google batch that hits the implicit cache the engine's flat 50% _overstates_ cost for the cached tokens, and OpenRouter does not discount non-token components at all.

  **The durable-steps round (1.0.0-alpha.10) — step-ledger integrity, queue and lease hardening, payload spilling, definition versioning, and an embeddable console:**

  _Breaking changes and the migration for this round are collected at the end of this section rather than repeated under each item._

  **Step ledger integrity.**

  - **Two durable steps sharing a key now fail loudly.** Steps are keyed by name rather than ordinal position, which is what lets a run survive renaming and reordering the code around a step; the debt is that two steps sharing a key silently answer each other's results. Asking for the same key twice in one stage invocation throws `DuplicateStepKeyError` (exported, with `isDuplicateStepKeyError`), naming the key and the kind and position of **both** uses. The guard existed but was useless where it mattered most: `ctx.step.ai.map`'s per-item catch turned any throw into a `{ status: "failed" }` verdict, so a map whose item keys collided with another step **completed successfully** with fabricated per-item failures. Those catches now rethrow it, and the local executor marks it non-retryable, so the stage fails terminally on the first attempt instead of burning the host's whole retry budget on a collision no attempt could resolve. When one item of a map raises the duplicate key and another raises a control-flow signal, the duplicate key wins: preferring the suspension surfaced it, the poll replayed the stage, and the same duplicate key came back one replay later — a correct report, after a poll cycle spent on a stage that could never finish, because a suspension recurs on the next replay and a duplicate key cannot fix itself. No suspension is lost, because a control-flow error is thrown after its step's ledger row exists (`StepInFlight` after a claim found a live lease, `StepSuspend` after the row recorded its handle and deadline), so the row and everything it holds survive the stage failing and the replay after the fix answers it from the ledger.
  - **A step that completed with no value is recorded as such.** `PrismaStepLedger`'s patch mapping excluded `result` whenever the value was nullish, so a step that finished with no value wrote nothing. On an `UPDATE` that leaves the _previous_ attempt's result in the row rather than clearing it, and now that re-running a stage can preserve a step row instead of deleting it, every later replay read the stale value back — permanently, and on Postgres only, because the in-memory ledger always wrote the `null` and so nothing caught it. `StepRecordPatch` now states the one rule every field follows: a key that is absent, or present holding `undefined` — which is what a spread of an optional property produces — leaves that column alone; any other value, **`null` included**, is written. `PrismaStepLedger` and `InMemoryStepLedger` implement it identically, where before they disagreed on `result`, `error`, `leaseExpiresAt`, `deadlineAt` and `waitState` whenever a key was explicitly `undefined`, and `stepLedgerConformanceSuite` holds any ledger to it.
  - **A step's outcome is recorded first-write-wins.** The write that records a step's outcome is a compare-and-set against the row still being open, instead of a blind update. Both the lease and the reopen-on-retry path can decide a step is takeable, so a wrong liveness verdict can put two workers inside one body; the ledger stays correct regardless. Whichever worker checkpoints first owns the outcome and the loser **parks** on what is recorded, so two workers can no longer return two different answers for one step, and a body that threw can no longer bury a success another execution already committed. The same constraint covers the wait/signal deadline write — a delivered signal now beats the timeout that was about to fail it — and the `onReclaim: "fail"` refusal. A conflict is reported, not raised: a WARN plus a `step.outcome-conflict` annotation carrying the step id, kind, recorded status, attempt and `externalKey`. The ledger stayed consistent; what the annotation tells you is that the _body_ ran more than once, which is when a duplicate external effect is possible.
  - **Re-running a terminally failed stage keeps a live batch handle.** Executing a stage whose status is `FAILED` used to clear its entire step ledger, destroying the row holding an in-flight batch's handle and its external key — so a stage that failed terminally while a batch was still being processed, and still being billed, lost the only record of it. The clean start is now reached by re-opening those rows rather than deleting them: every `run` row carrying an `externalKey` goes back to `running` with no lease, so the replay takes it over and executes the body again exactly as a deleted row would have, but the row, its key and its last result survive and the body is told `isReclaim: true`. Waits, signals and sleeps hold only timers and are still cleared so the new attempt re-derives them. `StepLedger` gains an optional `clearExcept(stageRecordId, keepStepIds)`; the bundled in-memory and Prisma ledgers implement it, and a third-party ledger without it falls back to the old whole-ledger clear with the kernel logging the external keys it is about to drop.
  - **Two source files no longer contain a raw NUL byte.** `core/step-external-key.ts` and `testing/shadow-runs.ts` embedded a literal NUL as a key separator inside a template literal, which made git treat both as binary: no textual diff, `grep` skipped them, and a merge on either was a binary conflict. Both now write the same character as the `\u0000` escape, which produces an identical string, so no external key changes. A convention test keeps every source file free of them. In the same spirit, every `StepLedger` test double is built from one shared wrapper whose forwarding list is checked against `keyof StepLedger` at compile time, so a new optional port method cannot be silently dropped by a hand-written object literal again.

  **Queue and lease hardening.**

  - **Fenced job acknowledgements.** `dequeue()` returns `startedAt` — the attempt stamp of that claim — and `complete`, `fail` and `suspend` take an optional `JobAckFence` (`{ startedAt, attempt }`) and return `"acknowledged" | "superseded"` instead of `void`. A worker that stalls past the lease threshold has its job rescued by `releaseStaleJobs` and re-claimed by someone else; without a fence its eventual `complete()` marked the _new_ attempt COMPLETED and discarded the work that attempt was really doing. The fence conditions the write on the job still being the RUNNING attempt it describes, so a stale acknowledgement writes nothing and says so. The built-in hosts pass it automatically, log a superseded acknowledgement, and skip the `run.transition` the newer attempt owns. Called without a fence the methods keep the old unconditional behaviour, so a transport that cannot carry the stamp still works.
  - **A fenced acknowledgement of a job that no longer exists reports `"superseded"` on both transports.** `InMemoryJobQueue` threw `Job not found` where `PrismaJobQueue` returned `"superseded"` — its fenced acknowledgement is an `updateMany` whose `WHERE` simply matches nothing — so a redrive that deleted a job row underneath its worker through `deleteByRunAndStages` turned a benign no-op into an error against the fake alone. `JobAckOutcome` already named deletion as one of the things `"superseded"` covers. Unfenced, naming a job that does not exist is still an error on both, because there is nothing to condition the write on.
  - **The Postgres job lease runs on the database clock.** The claim stamps `lockedAt`/`startedAt` with `now() AT TIME ZONE 'UTC'`, `touchJob` renews it the same way, and `releaseStaleJobs` derives the deadline in the same statement rather than computing `Date.now() - threshold` in the application. Previously a host whose system clock ran an hour behind wrote a lease an hour in the past and the next sweep — on any host — reclaimed a job that had only just been claimed and ran it twice. `staleLeaseThresholdMs` is now a duration measured by the database, not a deadline your process computes; this is the shape pg-boss, Graphile Worker, River and Oban all use. SQLite keeps the application-clock comparison (one process, one clock), and `PrismaJobQueueOptions.now` no longer affects the Postgres lease stamps. The durable-step lease was deliberately left on the application clock: its comparison is kernel code over a portable `StepLedger`, not a database predicate, so moving it means storing a lock time plus a duration instead of an absolute deadline. That column change is written down in `12-durable-steps.md` rather than performed here; NTP bounds the exposure against a five-minute default.
  - **Two-tier lease expiry with distinguishable reasons.** The heartbeat (`staleLeaseThresholdMs`, measured from `lockedAt`) only detects a worker that _stopped_; a worker that is alive but wedged keeps heartbeating and holds its job forever. A coarse absolute cap now sits beside it: `jobAbsoluteTimeoutMs` (new host option, default **one hour**, `0` disables) is measured from `startedAt`, which no heartbeat refreshes, so it always fires. Both sweeps stamp `lastError` with an exported prefix — `LEASE_HEARTBEAT_LOST` (requeued PENDING) and `LEASE_ABSOLUTE_CAP` (failed terminally, because a job that hung for the whole cap will hang again). The heartbeat tier sweeps first, so a dead worker's job is retried rather than dead-lettered. `lease.reapStale` gained `absoluteTimeoutMs` and returns `{ released, expired }`; `runMaintenanceTick` reports `staleExpired` beside `staleReleased`. `JobQueue.expireRunawayJobs` is optional on the port — an adapter without it simply has no absolute tier.
  - **Opt-in per-group fairness in the dequeue (PostgreSQL).** `createPrismaJobQueue(prisma, { fairness: { maxConcurrentPerGroup, groupBy } })` stops one tenant saturating a shared queue. It is a concurrency cap, not a reordering: a group already holding its share of the RUNNING pool is excluded from the claim, which leaves a quiet group's job as the only candidate. No ordering rule can achieve this — the flooding group's next row is re-ranked to the front the instant its previous one is claimed. `EnqueueJobInput.groupKey` names the group for direct callers; kernel-driven workflows point `groupBy` at a field of the run config, e.g. `"config.tenantId"`. `maxConcurrentPerGroup` has no default, because the right value is a function of your worker pool. Default behaviour is unchanged and the default claim statement is byte-identical to before. Fairness is off by default because it costs materially more on a deep queue — measured on Postgres 16 over 200 sequential claims: 0.94x at 1k ready jobs / 5 groups, 1.64x at 10k / 10, 2.19x at 50k / 100.
  - **Cancellation reaches a running body.** `run.cancel` marked the run and purged the queue, and the job executing at that moment ran to completion — a ten-minute model call, a `waitFor` about to poll — before its outcome was rejected by the ghost-job guard. The stage context now carries `ctx.abortSignal` (the same object as `step.abortSignal` inside every `ctx.step.run` body; named `abortSignal` so it is not confused with `waitForSignal`), aborted from the host's job lease heartbeat: `executeJobWithHeartbeat` dispatches the new `job.heartbeat` command on `jobHeartbeatIntervalMs`, which renews the lease and reports the run's status and whether this worker still holds the job, and aborts with a `StageAbortedError` whose `reason` is `"cancelled"` (the run is `CANCELLED`) or `"lease-lost"` (the job lease was released or re-claimed). After a `"cancelled"` abort a `run` body that finishes is recorded as `failed` with the cancellation as its error rather than `completed`, no retry is spent, and `waitFor` checks the signal before it polls. A `"lease-lost"` body's outcome is still recorded — the step row's own lease and compare-and-set decide the owner. `job.execute` takes an optional `abortSignal`; without one (a direct dispatch, a `stage.pollSuspended` replay, a remote activity worker) the signal never fires. `stageAbortReason(signal)` is exported. The test harness gains `cancel(workflowRunId, reason?)` and runs `tick()` under the heartbeat on a short wall-clock interval (`jobHeartbeatIntervalMs`, default 10 ms) so a body can `await` its own abort.
  - **`run.reapStuck` no longer enqueues inside the kernel transaction.** Its PENDING-stage-without-job recovery sweep moved to the post-commit path every other handler uses. It was safe in practice, but it was the same shape as the bug that wedged 62 runs in 100 before alpha.8; the handler now carries a comment stating the invariant so the pattern does not come back.

  **Operability.**

  - **Claim-check spilling for payloads that can grow without bound.** The engine has no payload ceiling, which is right for AI work and also why it needed an escape hatch: a very large step result was simply a very large row, read back in full on every replay. Stage outputs already went to the blob store; the same claim check now covers the two other unbounded write paths. A `workflow_steps.result` above `spillThresholdBytes` (new `createKernel` option, default 64 KiB) is written to the `blobStore` and the row keeps a `{ "$wfSpill": 1, key, bytes }` reference, resolved before the value reaches your stage — no wiring, because `createKernel` wraps the `stepLedger` it is given, so every step outcome write spills the same way: `run` and `waitFor` results, `ctx.step.ai.*` results and a map item's failed verdict; every read resolves, including a replay answered from the ledger and a worker parked on another worker's outcome. Clearing a stage's ledger (a redrive, a fresh attempt of a terminally failed stage) deletes its spilled blobs; a partial `clearExcept` keeps the blobs of the rows it keeps. The `StepLedger` port is unchanged. Job payloads spill on request through the new `createSpillingJobTransport(transport, { blobStore, thresholdBytes })`; pass the wrapped transport to both `createKernel` and your host. Consumers who deliver job messages through their own push queue and call `host.handleJob(msg)` directly must resolve the payload themselves with `createPayloadSpill({ blobStore }).unpack(msg.payload)`. The threshold is **soft** — a payload above it is spilled, never rejected — and 64 KiB is the largest round value that leaves a whole message envelope under Cloudflare Queues' 128 KiB limit (SQS is 256 KiB) while sitting two orders of magnitude above Postgres's ~2 KiB TOAST threshold. Reading a spilled value through a different blob store than the one that wrote it throws the new `SpilledPayloadUnavailableError`. Measured on one stage with two large step results: 520,022 inline bytes before, 224 after; a 300,036-byte job payload becomes a 79-byte queue row. Deliberately **not** spilled: `workflow_runs.input`/`.output`/`.config`, `workflow_stages.suspendedState`, annotation values and log metadata — those rows are part of your read model, and the claim check is applied only to rows that are engine plumbing. Spilling composes with the per-group fairness cap below: replacing a payload with a claim check hid a `groupBy` configured on a payload path (`"config.tenantId"`) and collapsed every spilled job into one anonymous group, losing starvation protection for exactly the tenants whose payloads are largest. `createSpillingJobTransport` discovers the wrapped queue's `fairnessGroupBy` (or takes an explicit `groupBy` of its own), hoists the value at that path onto `EnqueueJobInput.groupKey` before packing, and re-exposes the path as its own `fairnessGroupBy`; the fairness statement falls back to the hoisted `_groupKey` when the configured path is absent from the row.
  - **A named degraded mode for a failing event sink.** A refusing event sink used to surface as retries and silence. `outbox.flush` now returns `{ published, failed, deadLettered, eventSinkStatus, eventSinkError? }`, with `eventSinkStatus: "degraded"` when at least one event could not be published; `runMaintenanceTick` reports the same four fields, and a tick whose flush threw outright also reports degraded. The Node host exposes `getStats().eventSink` (`{ status, since, consecutiveFailures, deadLettered, lastError }`), logging one line on each transition rather than one per tick, and logging unconditionally whenever events were dead-lettered — the point at which delivery genuinely cannot proceed on its own and needs `plugin.replayDLQ`. The serverless host returns the same fields per tick, having no process to carry the state. `createEventSinkMonitor()` / `EventSinkHealth` are exported for consumers running their own loop. A degraded sink never stalls a run: the committed poller, not the sink, is what advances one, and there is a test for exactly that. `failed` and `deadLettered` are disjoint. `failed` was every released event id, which included the ones dead-lettered in the same pass — a dead letter is released so a replay can still find it in sequence, but it does not retry on its own and `deadLettered` already reports it, so a single event was counted twice. `failed` now means what `MaintenanceTickCounts.eventsFailed` documents, which is what the next flush will retry: the events whose emit threw, plus the later events of those same runs held back to keep per-run order.
  - **Suspended-stage single flight keeps its `nextPollAt` lease.** Postgres advisory locks were evaluated as a replacement and rejected; the reasoning is recorded at the claim site and in the execution-model docs. A session lock belongs to the connection, not the task, so two pollers handed the same pooled connection both win it; PgBouncer in transaction mode does not support session locks; the serverless host has no session to own one; and a session lock taken inside a consumer's own transaction is not released at their `COMMIT` and lives in a 64-bit namespace that is global to the database and invisible to row-level security. No behaviour change.

  **Definition versioning.**

  - **A run resolves against the definition it started under.** Nothing previously defined what happens when a workflow definition changes while runs are in flight: a stage could be added, removed or reordered under a run that was midway through, and the run resolved against the live builder, so it silently changed shape. `run.create` now stamps the run with a definition version and records the structure that version identifies as a content-addressed snapshot, and every path that resolves a definition for an existing run refuses to serve it under a different structure. **What the version identifies** is the pipeline's _structural contract_: stage ids in definition order, execution groups, declared dependencies and modes, and the normalised JSON Schema of every stage's input/output/config schema plus the workflow's own. Stage `name`, `description` and the bodies of `execute`/`checkCompletion`/`estimateCost` are deliberately excluded, so editing what a stage _does_ never forks an in-flight run. `workflow.definitionVersion` reads `sha256-…`; `getDefinitionSnapshot()` returns the structure it hashes; `defineWorkflow(…).version("2026-09-04.1")` declares one yourself, and re-registering it with a different structure throws `DefinitionVersionConflictError`.
  - **Rolling deploys are safe by construction.** `run.claimPending` claims a pending run only when this build presents that run's `(workflowId, version)` pair, so old hosts finish their own work and new hosts never adopt an incompatible run. Turn it on by building the registry with `createWorkflowRegistry(workflows)`, which implements the optional `WorkflowRegistry.listWorkflows()` the filter derives from; a hand-written `{ getWorkflow }` registry cannot enumerate, so claiming stays unfiltered, and `serves: "all"` restores the old predicate explicitly. For a run already RUNNING when a deploy lands, `job.execute` returns `{ ghost: true, ghostReason: "version" }`: the job is re-delivered for a host that can serve it and the run is **not** failed. `run.transition`, `stage.pollSuspended` and `run.reapStuck` all leave such a run untouched — the reaper especially, because a run nobody on this build touches crosses the stuck threshold looking exactly like a wedged one, and the suspended-stage poller hands back the claim it took before discovering the mismatch, so an unserving host cannot starve a serving one. The claim predicate decides this in the query on both of its arms: a pinned run is claimable only by a host presenting its `(workflowId, version)` pair, and an _unpinned_ run — one created before the consumer's migration — only by a host whose `serves` names its workflow. Without that second restriction every host in the fleet claimed the whole pre-migration population, including hosts whose registry had never heard of the workflow, which then adopted the run only to fail it with `WORKFLOW_NOT_FOUND`; and an empty `serves` now claims nothing, because a host that serves no workflow has no work. Version filtering only ever had to work on a fleet, which is the one situation it exists for.
  - **Every path that takes work applies the same filter, in the query that takes it.** `getSuspendedStages(beforeDate, { limit, serves })` returns only the stages of runs this build serves, oldest poll deadline first, capped at the handler's `maxChecks`, where it previously returned every ready row for the handler to slice in JS. A stage this build cannot serve is handed back to the deadline the row already had rather than released to `now`: released to now it was re-claimed and re-released every tick for the whole deploy, two version-bumping writes each time, and because it never left the ready set it permanently occupied a candidate slot and pushed servable stages out of the window. The job dequeue narrows too — a job carries its run's version on the payload as `_definitionVersion`, and `dequeue({ serves })` filters on it, where before, in a fleet of N hosts, each dequeue had an (N−1)/N chance of landing on a host that could not execute what it claimed. The kernel's version-ghost handling stays the backstop, for an adapter that cannot express the filter and for a run whose version changed between the query and the claim.
  - **Declining a job no longer spends its attempt budget.** `JobQueue.defer(jobId, nextPollAt, reason, fence?)` is a new optional port method that returns a claimed job to `PENDING` and gives back the attempt the dequeue counted. `fail(..., true)` is the wrong shape for work a host declines rather than fails: a version mismatch clears when a deploy finishes, not on the next tick, so re-delivering through the failure path exhausted the three-attempt budget in about fifteen seconds and took the job row terminal. A transport that does not implement `defer` falls back to the bounded retry, which is correct but still bounded.
  - **`serves` is reachable from a host.** `runMaintenanceTick` forwards it, and both shipped hosts take `serves?: readonly ServedDefinition[] | "all"` as configuration, so the documented `serves: "all"` escape hatch can actually be used; leaving it unset still means "derive it from the registry". `Kernel.servedDefinitions()` is what a host passes to the dequeue when it has no configuration of its own.
  - **An unmigrated database really does still start.** The Prisma adapter's versioning answer came from the _generated client_, which says yes from `prisma generate` onwards — before `migrate deploy` on a first migration, and on any rolling deploy that ships code ahead of schema. Against a database in that state the host could not claim a single run and the operator saw a raw `42703`. The structural check still runs synchronously, and the _database_ is now confirmed once, lazily, the first time a versioning-sensitive path runs, through a catalogue read (`to_regclass` and `pg_catalog.pg_attribute` on Postgres, `sqlite_master` and `pragma_table_info` on SQLite) that answers "absent" instead of raising — so it cannot abort a transaction the kernel is running inside, which is the one thing this adapter must never do. The capability state is shared by reference with every transactional clone, so the probe runs once per client and a downgrade one clone discovers is visible to all of them. `PrismaWorkflowPersistenceOptions.definitionVersioning` skips both checks: `false` for a client whose schema carries the models against a database deliberately left unmigrated, `true` for a model surface the structural detection cannot see, such as a hand-written wrapper or a proxy.
  - **`run.listVersions`: has it drained?** A new command answering the question a pinned fleet creates — which versions still have runs, and are any stranded with no host. Each entry carries per-status `counts`, `total`, `active`, `drained`, `servedHere` and `oldestCreatedAt`; `unservedHere` is the list to act on. On an unmigrated database the result is `{ supported: false, versions: [], unservedHere: [] }` rather than a misleading empty answer. There is no automatic reaper: a host cannot distinguish "nobody serves this" from "a peer on the old build does", so a per-host timeout would destroy runs mid-deploy.
  - **Shadowing catches an incompatible change in CI.** `@bratsos/workflow-engine/testing` gains `shadowRuns`, `shadowVersions` and `assertShadowCompatible` — Cadence's Workflow Shadower for a step ledger. `shadowVersions` needs no run ids: it finds every definition version that still has live runs and diffs the recorded snapshot against your candidate build, so an incompatible pipeline change fails a build rather than a production run. It verifies structure and the configs and outputs each stage recorded, not that a stage body emits the same step keys — those exist only once the code runs.
  - **`run.redrive`: retry, restart and rerun without destroying the attempt.** `run.rerunFrom` covered only "rerun from this stage", and it deleted the failed stage row and everything after it. `run.redrive` covers Conductor's three verbs on one command — `from: { kind: "lastFailure" | "start" | "stage" }` — with Step Functions' framing for the rest: the same run id, an incremented `redriveCount`, no branching into a second execution. **Every stage record it supersedes is first archived** as a stage-scoped annotation under `run.supersededAttempt`, carrying its status, error, timings, metrics, output pointer and whether the record was `reopened` or deleted. `definitionVersion: "latest"` (or an explicit registered version) moves the run onto another version, which is also how a run stranded at a version nothing serves is rescued. `run.rerunFrom` still works with an unchanged result shape, now shares `run.redrive`'s behaviour including the preserved attempt, and is deprecated.
  - **`run.redrive` keeps the resumed stage's progress.** For `from: { kind: "lastFailure" }` and `{ kind: "stage" }` the stage record being resumed from is no longer deleted and recreated; it is reopened in place — back to `PENDING`, `attempt` incremented, the old attempt's error, output, suspended state and timings cleared, `version` bumped — so its durable step ledger, keyed by that record's id, survives. Every `completed` step row is kept and answered from the ledger (a stage that completed 9 of 10 `ctx.step.run` steps re-runs only the tenth), and a kept step's external key — derived from the stage record id — is unchanged, so provider-side idempotency keys still match. Rows naming an external effect that did not complete are re-opened exactly as the engine's own job retry re-opens them; waits, signals, sleeps and failed rows with no external key are dropped through `StepLedger.clearExcept`, and a ledger without it falls back to a full clear with the same record of what was lost. Stages after the resumed one are still archived and deleted, and `from: { kind: "start" }` still replaces everything. `UpdateStageInput.completedAt` and `duration` accept `null` so the reopen can clear them. `run.rerunFrom` gets this too, since it delegates.
  - **A redrive no longer orphans a billed batch silently.** Where `run.redrive` does drop step rows — a restart, the stages after the resumed one, or a `StepLedger` that cannot clear selectively — a `run` row may hold the external key of a provider batch that is still being processed and still being billed. Before the drop, every abandoned row that names an external effect is recorded twice: as `abandonedSteps` (`stepId`, `status`, `externalKey`) on that stage's `run.supersededAttempt` annotation, and as a `WARN` log on the run naming how many rows were dropped and that any effect still in flight has to be found by its external key. The annotation is there as well as the log because logs rotate; both name only rows that were actually dropped, so the field is absent when nothing external was abandoned — which is every resume on a ledger with `clearExcept`. `run.rerunFrom` gets this too, since it delegates.

  **The console (new package `@bratsos/workflow-engine-console`).**

  - An optional, embeddable operational console: a framework-agnostic `(Request) => Promise<Response>` handler plus a prebuilt UI you mount inside your own application, so you no longer have to build a screen to answer "what happened to this run". **It never opens a database connection.** You construct its read port from the Prisma client — or the transaction client — you already have, so its reads run in your session, inside your transaction, under your row-level security, with authentication already decided upstream. A separate dashboard process with its own connection string would be a second session and therefore a second security context, and no configuration recovers the tenant scoping once that happens.
  - Mount it anywhere: Next.js route handlers, Hono, Cloudflare Workers, Deno and Bun call the handler directly; Express, Fastify and bare `node:http` go through `toNodeHandler` from `@bratsos/workflow-engine-console/node`.
  - **Read-only by default, and `authorize` defaults to deny.** Authorisation is a per-request callback over an action vocabulary (`runs.read`, `run.cancel`, `deadLetters.replay`, …) rather than HTTP methods, and a throw inside it denies rather than allows. Writes go through kernel commands (`run.cancel`, `run.rerunFrom`, `plugin.replayDLQ`), never SQL, so they keep the kernel's leases, idempotency and outbox events; `onAction` gives you the audit trail.
  - Views: runs list (keyset-paginated, filtered by status, workflow, workflow type and time range), run detail with its stage timeline, step ledger, annotations, logs and outbox event timeline, queue health, suspended stages, workers, dead letters, and cost and tokens rolled up by workflow and by day. The UI is Preact compiled into the package at our build time — no build step for you, no frontend toolchain in your dependency graph, nothing loaded from a CDN, and no filesystem access, so it runs unchanged on Workers and edge runtimes. About 15 kB gzipped. It polls (5 s by default), pauses on a hidden tab, reads in light and dark, and scopes its CSS so it does not restyle the page it is mounted in.
  - **It shows and filters by definition version.** The read port selected explicit column lists written before definition versioning existed, so it could not see either new column whatever the database held. `RunSummary` now carries `definitionVersion` and `redriveCount`, so the runs list and the run detail both have them, and `RunListFilters.definitionVersion` (`GET /api/runs?definitionVersion=…`) answers the question versioning creates: show me everything still pinned to the old version. The runs table gained a Version column — shortened, full value on hover, with the redrive count as a `+N` suffix — the filter bar a version input, and the run detail two entries.
  - **Writes go through `run.redrive`, so a stranded run is recoverable from the console.** `POST /runs/:id/rerun` dispatched the deprecated `run.rerunFrom`, which refuses a `CANCELLED` run and has no way to re-pin a definition version — so the one remedy for a run pinned to a version no deployment serves any more was unreachable from the only screen an operator has. It now dispatches `{ type: "run.redrive", workflowRunId, from, definitionVersion? }`. The request shape is a superset of the old one: `fromStageId` still means "from this stage", `from` takes `{ kind: "lastFailure" | "start" | "stage" }`, and `definitionVersion` takes `"latest"` or a registered version. A malformed `from` is a 400 rather than a fall back to the default mode, because an operator who asked to restart a whole run must not silently get a retry of one stage. The UI offers _Redrive on latest version_ on any run carrying a pinned version. The `run.rerun` **action name is unchanged**, so an existing `authorize` or `onAction` still matches; a custom kernel that implemented only `run.rerunFrom` must now also accept `run.redrive`.
  - **An operator can deliver a durable-step signal from the console.** A stage suspended on `ctx.step.waitForSignal` — the human-approval case — had no way to be finished from the one screen an operator has. A new write action `step.signal` and route `POST /runs/:runId/stages/:stageId/steps/:stepId/signal` (body `{ payload }`, optional, defaults to `null`) dispatch `{ type: "step.signal", workflowRunId, stageId, stepId, payload }` on the kernel. It is gated by `authorize` like the other writes (the context and the `onAction` event carry `stageId` and `stepId` alongside `runId`), and the kernel's refusals become statuses rather than 500s: an unknown run or stage is a 404, a step that is not a pending signal is a 409, both with the kernel's message. `StepSummary` gains `externalKey` next to `kind`, `status` and `deadlineAt`, so the run detail offers _Deliver signal_, with a validated JSON payload box, only on a step with `kind === "signal"` and `status === "pending"`, and shows the external key on `run` steps. A custom `ConsoleKernel` must now accept `step.signal`.
  - `npx workflow-console --config ./console.config.mjs` serves the same handler on a local HTTP server for repositories with no web application to mount into. Loopback only, no authentication, read-only by default; connecting directly with `--database-url` requires `--allow-direct-connection`, which acknowledges that the connection is a second session and will not be scoped by your policies.
  - Nothing in the engine depends on this package.

  **Index changes (one migration, measured).** The reference schema's index set had no support for "most recent runs first", which is the default view of any operational screen, and the dequeue's `createdAt` tiebreak was not covered at all. Composite indexes replace or add to `workflow_runs`, and the `job_queue` claim index gains the tiebreak:

  ```prisma
  model WorkflowRun {
    // replace @@index([status]) and @@index([workflowId])
    @@index([createdAt(sort: Desc), id(sort: Desc)])
    @@index([status, createdAt(sort: Desc), id(sort: Desc)])
    @@index([workflowId, createdAt(sort: Desc), id(sort: Desc)])
    // the run claim
    @@index([status, priority(sort: Desc), createdAt])
    // definition versioning
    @@index([definitionVersion])
    @@index([status, workflowId, definitionVersion])
  }
  model JobQueue {
    @@index([status, priority(sort: Desc), createdAt])  // replaces @@index([status, priority])
    @@index([status, createdAt])                        // added
  }
  model OutboxEvent {
    @@index([dlqAt])                                    // added
  }
  ```

  Every replacement is a composite whose leading column is the same, so it serves every lookup the index it replaces served. Measured against 500k runs, 1.5M jobs and 2M outbox events: "newest runs first" 244 ms → 0.03 ms, filtered by status 94 ms → 0.03 ms, oldest pending job 6.6 ms → 0.02 ms, dead letters 42 ms → 0.14 ms. The dequeue was measured separately at flat priorities: 0.55 ms at 1,000 ready rows and **26.7 ms at 50,000**, because without the tiebreak in the index a deep queue reads and sorts every PENDING row on every claim; with it, 0.03 ms and 0.04 ms, flat with depth. That one costs real space — `(status, priority)` is nearly all duplicate keys, which btree deduplication collapses, and adding `createdAt` makes every key distinct: 1 MB → 10 MB at 150,000 rows. The engine's own hot paths are unchanged within noise (`claimNextPendingRun` 18.4 → 19.2 ms, `getStuckRuns` 13.0 → 13.3 ms, both warm). Postgres users writing migrations by hand should prefer a partial index for the dead-letter one (`WHERE "dlqAt" IS NOT NULL`); Prisma cannot express one.

  The run claim needs an index of its own. `claimNextPendingRun` issues against `workflow_runs` the same shape the dequeue issues against `job_queue` — `status = 'PENDING' ORDER BY priority DESC, "createdAt" ASC LIMIT 1 FOR UPDATE SKIP LOCKED` — `maxClaimsPerTick` times per tick per host, and none of the list orderings can serve it, because `priority` is in none of them, so the claim read every `PENDING` row and top-N sorted it. Measured on Postgres 16 at 300k runs / 60k pending: 11.8–15.1 ms before, 0.008–0.022 ms after, for 9 MB of index. The two definition-versioning indexes are narrower than they look: `(definitionVersion)` serves a lookup narrowed to one version with no workflow, and `(status, workflowId, definitionVersion)` is the stand-in for the `@@index([status])` the list orderings replaced — a status count runs index-only off it — and also narrows the version-filtered claim. Neither covers `run.listVersions`, which plans a parallel sequential scan whatever is present: that handler passes no status filter, and its aggregate wants a `MIN("createdAt")` no index here carries.

  `workflow_definitions` deliberately has no `(workflowId)` index: the compound primary key already leads with that column, so a lookup by workflow alone plans identically either way (0.188 ms against 0.187 ms at 20k rows), and no query in the engine reads that table by workflow alone. An earlier draft of the hand-written migration in the upgrade guide created one — if you already ran it, `DROP INDEX CONCURRENTLY IF EXISTS "workflow_definitions_workflowId_idx";` is safe, and the guide now says so.

  **Breaking changes in this round:**

  - **`JobQueue` / `JobTransport`.** `dequeue()` returns `startedAt`, and `complete`, `fail` and `suspend` return `"acknowledged" | "superseded"` instead of `void` and take an optional trailing `JobAckFence`. Custom adapters must widen those three return types; the conformance suite covers both the fenced and unfenced paths. A **decorator** around a transport must forward the fence explicitly — a delegation that drops the optional parameter still typechecks, and silently turns every fenced acknowledgement back into an unconditional write. `dequeue(options?)` takes `DequeueOptions.serves`; a transport that cannot express the filter may ignore it, because the kernel's version-ghost handling is the backstop. `defer(jobId, nextPollAt, reason, fence?)` and `expireRunawayJobs(absoluteTimeoutMs)` are new **optional** methods — a transport without `defer` re-delivers a declined job through the bounded retry, and one without `expireRunawayJobs` has no absolute lease tier. A fenced `complete`, `fail` or `suspend` naming a job row that no longer exists must return `"superseded"` rather than throw; unfenced, it stays an error. `JobTransport.fairnessGroupBy` is a new optional readonly property, read by `createSpillingJobTransport`.
  - **`StepLedger`.** `StepRecordExpectation.attempt` is now optional (omit it to match any attempt) and `compareAndSet` implementations must honour that. `clearExcept(stageRecordId, keepStepIds)` is optional; a ledger without it falls back to the whole-ledger clear. The same forwarding rule applies to a ledger decorator. `StepRecordPatch` now has one documented rule that a custom ledger must follow and that `stepLedgerConformanceSuite` checks: an absent key, or a key holding `undefined`, leaves that column alone; every other value, **`null` included**, is written. A ledger that skipped nullish values — as the bundled Prisma one did for `result` — records "completed with no value" as "unchanged", and the previous attempt's result then replays forever.
  - **`WorkflowRunRecord`** gains `definitionVersion: string | null` and `redriveCount: number`, and `RunCreateResult` gains `definitionVersion`. Custom persistence adapters must implement four new `PersistenceCore` methods — `supportsDefinitionVersioning`, `insertDefinitionIfAbsent`, `getDefinition`, `countRunsByDefinitionVersion` — and accept the new `serves` option on `claimNextPendingRun`. An adapter without the schema can return `false` / `null` / `[]` and ignore `serves`. **`getSuspendedStages` gained a second parameter**, `options?: { limit?, serves? }`, and now owns both narrowings: it must return rows oldest `nextPollAt` first and cap at `limit`, where the handler used to order and slice in JS. An adapter that ignores the cap makes the handler's `maxChecks` window fill with rows it cannot act on; an adapter with no `definitionVersion` column may ignore `serves`, because such a database has no pinned runs and ignoring it is exact.
  - **`claimNextPendingRun` with an empty `serves` claims nothing**, and an unpinned run is claimable only by a host whose `serves` names its workflow. Both are deliberate: a host that enumerates no workflow has no work, and the pre-migration population is not every host's to adopt. Omit `serves` — or pass `serves: "all"` at the host — for the pre-1.0 predicate.
  - **`JobExecuteResult.ghostReason`** gains a third value, `"version"`. The built-in hosts re-deliver it like `"race"`.
  - **`run.claimPending` no longer fails a claimed run whose workflow is missing from the registry** when the registry can enumerate itself. Previously such a run was adopted and marked `FAILED` with `WORKFLOW_NOT_FOUND`; it is now left `PENDING` for a host that has the workflow, and reported by `run.listVersions`. A non-enumerating registry, or `serves: "all"`, still gives the old behaviour.
  - **`OutboxFlushResult`** gains `failed`, `deadLettered`, `eventSinkStatus` and `eventSinkError`; `MaintenanceTickCounts` gains the matching fields. `failed` counts only the events the next flush will retry — it excludes the ones dead-lettered in the same pass, which `deadLettered` reports — so the two populations are disjoint and a dashboard that adds them no longer double-counts.
  - **The reference Prisma schema drops `workflow_definitions (workflowId)`** and adds `workflow_runs (status, priority DESC, createdAt)`; see the index section above for the `DROP INDEX` if you ran an earlier draft of the hand-written migration.
  - **`PrismaWorkflowPersistenceOptions.definitionVersioning`** is the documented escape hatch that skips both the client check and the database probe. Left unset, the adapter now confirms the generated client's answer against the database once, lazily, with a catalogue read.
  - **`PrismaJobQueueOptions.now`** no longer affects the Postgres lease stamps, which come from the database clock.
  - **A reclaimed submit on a transport that cannot be searched** (Anthropic, OpenRouter) throws `BatchNotAdoptableError` — carried over from alpha.9, restated here because `batch: { onReclaim: "resubmit" }` is the opt-out.
  - **`run.rerunFrom` is deprecated** in favour of `run.redrive`.
  - **`workflow_steps` cascades from `workflow_stages`, and runs get a retention command.** `WorkflowStep.stageRecordId` had no foreign key, so deleting a run through the existing cascades left its ledger rows forever; the reference schema now declares `stage WorkflowStage @relation(..., onDelete: Cascade)` (constraint `workflow_steps_stageRecordId_fkey`; the migration guide has the guarded `ADD CONSTRAINT` for a table created from an earlier alpha). Nothing in the engine deleted runs at all, so there is now `run.purge` — `{ olderThan, statuses?, limit? }` → `{ purged, workflowRunIds }` — which clears the step ledger through the port, removes job rows and blobs, and deletes the run with everything under it; both hosts run it on the maintenance tick when given `retention: { olderThanMs, statuses?, limit? }` (off by default), and `MaintenanceTickCounts` gains `purged`. **Custom `WorkflowPersistence` implementations** gain two required methods, `listRunsForPurge(cutoff, statuses, limit)` and `deleteRun(id)`, both in the conformance suite.

  **Migration for this round.** Two nullable columns on `workflow_runs`, one new table, and the index set above. All additive, no backfill, and the index work is the only part with a real cost. **A database that has not been migrated still starts**, and so does one whose client is ahead of it: the Prisma adapter checks the generated client structurally for the `workflowDefinition` delegate, then confirms that answer against the database once, lazily, with a catalogue read that returns "absent" rather than raising, so nothing can abort a caller's transaction. Either "no" runs with versioning off. Set `definitionVersioning` explicitly to skip both. Runs created before the migration carry a null version and stay claimable, for life, by any host whose registry holds their workflow. The exact SQL, `CONCURRENTLY` where it matters, is in the database checklist of `migrations/migrate-0.13-to-1.0.md` — which also carries the `workflow_runs (status, priority DESC, createdAt)` index and the `DROP INDEX` for the `workflow_definitions (workflowId)` an earlier draft of it created; _Core Concepts → Definition Versioning_ explains what the version identifies and how a fleet drains one. `sql/enqueue.sql` is optional and separate: apply it in your own migration, after the engine's tables exist, only if you want the SQL enqueue.

  **Fixes from the benchmark round (1.0.0-alpha.8) — two long-standing defects, both present in 0.13.0 as well:**

  - **`run.claimPending` enqueued the first-stage job inside the claim transaction, so a fast job loop wedged the run it had just claimed.** The job transport is a separate connection that takes no part in that transaction, so the job row was visible while the run it named was still `PENDING` everywhere else. A worker whose job loop polled faster than the claim committed dequeued it, `job.execute`'s ghost guard discarded it as an orphan, and nothing re-enqueued it: the run sat `RUNNING` with no job until `run.reapStuck` reaped it minutes later. Measured on this worktree with a 2 ms job poll: **62 of 100 freshly created runs wedged; 0 of 100 after the fix** (0 of 200 at a 1 ms poll). Invisible at the 1000 ms default and worse the shorter the poll, which is exactly what a caller chasing near-synchronous behaviour reaches for. Two changes, either sufficient on its own: `run.claimPending` now defers the enqueue to the kernel's post-commit step, like `run.transition` and `run.rerunFrom` already did (the run is committed `RUNNING` before its job exists; `claimed[].jobIds` still carries the ids, and every claimed run's enqueue is attempted even if another's fails); and a job whose run is still `PENDING` is reported as a race rather than an orphan — `JobExecuteResult.ghostReason` is `"race"` or `"orphan"` alongside `ghost: true`, and both hosts re-deliver a `"race"` (through `fail(jobId, error, true)`, so the transport's usual backoff applies, while the job's attempt budget lasts) instead of throwing it away. A terminal run's job is still failed terminally, with no `run.transition`. `run.reapStuck`'s PENDING-stage-without-job sweep remains the backstop for a job lost after the commit, and the enqueue is idempotent on `(workflowRunId, stageId)`, so it cannot double-queue. **No migration.** A custom host that read `ghost` alone keeps working (it just keeps discarding racing jobs); read `ghostReason` to get the recovery.

  - **Stale-lease recovery did not work on a Postgres session that was not on UTC, so a crashed worker's job was never picked up.** The adapters' raw `FOR UPDATE SKIP LOCKED` statements bound a JS `Date`, which Prisma sends as a `timestamptz`; assigning that to the naive `timestamp` columns the schema declares — or comparing the two — converts it through the _session's_ `TimeZone`, while every column Prisma's model API writes is UTC. On a session at `Europe/Zurich` the dequeue wrote `job_queue.lockedAt` **two hours in the future** (measured: +7 200 000 ms; 0 ms after the fix), so a lease could never look stale, `releaseStaleJobs` released nothing, `touchJob` appeared to move the lease backwards, and a SIGKILLed worker's job stayed `RUNNING` forever. The same skew hit `workflow_runs.startedAt`/`updatedAt` from the run claim (so `run.reapStuck`'s inactivity window was wrong too) and `outbox_events.publishedAt`. `NOW()`, which 0.13 used, is wrong the same way. Every raw statement now converts its bound timestamps explicitly (`$n::timestamptz AT TIME ZONE 'UTC'`), so raw and model writes agree on any session timezone with nothing for the consumer to set; the Postgres conformance suite gained cases that run the dequeue, the lease sweep, `touchJob` and the run claim on a session pinned to `Pacific/Kiritimati` (UTC+14). **No migration:** keep the engine's timestamp columns as plain Prisma `DateTime` (naive `timestamp`), as the shipped `prisma/schema.prisma` declares them — a consumer who mapped any of them to `@db.Timestamptz` must revert that mapping, which is the only case where anything needs changing.

  - **The durable-step lease is documented as the crash-recovery dial it is; the behaviour is unchanged.** A benchmark measured crash resumption of a step-bodied stage as 74% slower in wall clock than re-running the whole stage, because a step left `running` by a killed process is held by its lease until it expires and the default is five minutes. That is a design decision, not an oversight: a ledger row carries no worker identity, so the lease is a step's only liveness signal, and releasing it early would risk executing a step body twice — the one thing the ledger exists to prevent. (`lease.reapStale` releases job leases only.) `StepRunOptions.lease` is the knob; it is now stated as such, with the recovery-latency consequence and how to size it, in 12-durable-steps.md, next to the host tuning knobs in 03-runtime-setup.md, and as a troubleshooting entry for "crash resumption waits minutes".

  **Fixes from the seventh consumer round (1.0.0-alpha.7, host-node 0.4.4) — `run.rerunFrom` wedged the run it was rerunning:**

  - `run.rerunFrom` deleted the stage records at and after the target execution group but never touched their `job_queue` rows, then re-enqueued the same `(workflowRunId, stageId)` with an unconditional insert. On a schema declaring `@@unique([workflowRunId, stageId])` the insert failed with `P2002` — post-commit, so the run was left wedged as `RUNNING` with a fresh `PENDING` stage and only the stale terminal job row, and `run.reapStuck`'s PENDING-without-job sweep re-enqueued through the same path and threw on every tick, so the run could never self-heal. On a schema without the unique, every rerun instead accumulated another job row per stage. Three changes, each of which fixes it on its own: `run.rerunFrom` retires the job rows of every stage record it deletes through a new `JobTransport.deleteByRunAndStages(workflowRunId, stageIds)` (this is what covers the downstream stages a rerun deletes without recreating — nothing would ever enqueue over their rows); `enqueueParallel` (and the built-in adapters' legacy `enqueue`) is idempotent on `(workflowRunId, stageId)`, replacing any row already queued for a pair in the same transaction as the insert and resetting `attempt`, `status`, `workerId`, `lockedAt`, `lastError` and `nextPollAt`, which also makes the reaper's recovery sweep safe on any schema; and the reference `prisma/schema.prisma` declares `@@unique([workflowRunId, stageId])` on `JobQueue`, covered by `jobQueueConformanceSuite` so both adapters are checked. The old row is deleted rather than marked terminal: it is a row for an execution whose stage record has just been deleted, so there is no stage row left for it to be history of. Verified against Postgres with the constraint in place: a failed 3-stage run rerun twice in a row ends with exactly one job row per stage and the stages before the rerun target still at `attempt 0`.
  - **Migration:** add `@@unique([workflowRunId, stageId])` to your `JobQueue` model. The index build fails while duplicate rows exist, and pre-upgrade reruns may have left some — collapse them first (keep the newest row per pair, with no worker mid-job) and then create the index; the 0.13 → 1.0 guide has the SQL. A deployment that cannot take the constraint yet still gets the fix, since the enqueue paths are idempotent either way; the constraint is what stops a custom `JobQueue` from writing a duplicate.
  - **Custom `JobQueue` / `JobTransport` implementations:** `deleteByRunAndStages(workflowRunId, stageIds)` is a new required method, and `enqueueParallel` must be idempotent on `(workflowRunId, stageId)` as described above. Both are in the published conformance suite.
  - `NodeHostConfig.workerId` reaches `job_queue.workerId`. The row is written by the job queue, which is constructed before the host and, given no `workerId` of its own, generated `worker-<pid>-<timestamp>` — an id matching no host, so a job row could not say which worker ran the stage unless the consumer remembered to pass the same id to `createPrismaJobQueue` as well. `createNodeHost(...).start()` now offers its `workerId` to the transport through an optional `JobTransport.adoptWorkerId(workerId): string`, implemented by `PrismaJobQueue` and `InMemoryJobQueue`: a queue built without an explicit `workerId` adopts the host's, a queue built with one keeps it and the host logs a single `workerId mismatch` line naming both ids. Drop the `workerId` argument from `createPrismaJobQueue(prisma)` under a host; keep it only where no host supplies one. The port method is optional, so a custom transport needs no change.
  - `@bratsos/workflow-engine-host-node` 0.4.4: a multi-stage run is no longer pinned to the worker that completed its previous stage. That worker is the one that dispatches `run.transition`, so it enqueued the next execution group in-process and went straight back to `dequeue()` while every other worker was still parked in its `jobPollIntervalMs` timer — measured with four identical workers, four 4-stage runs each ran on exactly one worker. The job loop now pauses for a uniform draw over `[0, postJobYieldMs)` after a _completed_ job (only that outcome enqueues a successor from this process), which gives the completing worker the same phase every competitor has. `NodeHostConfig.postJobYieldMs` defaults to `jobPollIntervalMs`; `0` disables the pause and restores the old behaviour. The tradeoff is latency on a run one worker keeps advancing, so the pause is skipped while the loop is draining a backlog — as soon as `dequeue()` returns a job from a different run than the one just completed, the worker stops pausing until the queue next comes back empty, so a backlog costs at most one pause rather than one per job. Correctness is unchanged either way (every stage always ran exactly once); this only decides which worker picks a stage up.

  **Fixes from the sixth consumer round (1.0.0-alpha.6) — `z.record` under OpenAI strict outputs:**

  - A `z.record()` reached OpenAI strict structured outputs (native and through OpenRouter, realtime and `:batch`) as `{ type: "object", propertyNames, additionalProperties: <schema> }` and every request was rejected with `'propertyNames' is not permitted` (strict mode permits neither keyword and has no map type). For the OpenAI target a record is now sent as an array of `{ key, value }` objects — an enum key constraint is kept on `key`; records nested in objects, arrays, tuples, union branches and `$defs` are covered; an optional record is nullable like any optional property — and the reply is rebuilt into the object before validation (last duplicate key wins), so the caller's Zod schema sees the original shape. `z.looseObject`/`.catchall()` objects are sent closed. Verified live on OpenRouter `openai/gpt-5-nano` through `generateObject`, `generateText` + `Output.object` and a one-item batch. The Google target is untouched (Gemini expresses records natively).
  - The inverse transform — optional-property nulls removed, record pairs rebuilt — is one pass, `restorePortableValue(value, jsonSchema)`; `stripOptionalNulls` stays exported as an alias. It runs in the realtime middleware (`generateObject`, `generateText` + `Output.object`; a streamed JSON reply is now restored too, its text deltas buffered per text part and emitted at `text-end`) and on the OpenAI/OpenRouter batch `getResults` path.
  - A schema keyword OpenAI strict mode cannot express and the engine has no rewrite for (`patternProperties`, `unevaluatedProperties`, `minProperties`, `maxProperties`, `unevaluatedItems`, `contains`, `minContains`, `maxContains`, `uniqueItems`, `not`, `if`/`then`/`else`, `dependentRequired`, `dependentSchemas`) now fails at the engine boundary with `UnportableSchemaError` (`path` as a JSON pointer, `keyword`, `target`; exported from the root entry) before any request is sent — a realtime call throws it, a batch submit fails with it — instead of a provider 400 per item.
  - `StageContext.attempt`, reported `undefined` in a stage body: the public `StageContext` has never declared it, so nothing changed; the stage row's `attempt` (`WorkflowStage.attempt`, via `ctx.stageRecordId`) is the source of truth.

  **Fixes from the fifth consumer round (1.0.0-alpha.5, host-node 0.4.3) — two orchestrating processes replayed the same suspended stage:**

  - `stage.pollSuspended` claims a suspended stage before doing any work on it. Two processes with orchestration on (or two overlapping ticks in one process) both read the same stage from `getSuspendedStages` and both ran its body — a durable stage's `execute()` replayed three to five times after its batch settled, and the app's persist transaction ran as many times; the run-level claim guarded only the final write. The handler now issues a version-guarded `updateStage(id, { nextPollAt: now + lease, expectedVersion })` per stage, outside the per-stage transaction, before `checkCompletion`, a replay or the wait-deadline check; a `StaleVersionError` means another poller holds it and the stage is skipped. The lease is `max(pollInterval, 60s)`, bounded by `maxWaitUntil` while that deadline is ahead. Every outcome still writes `nextPollAt` explicitly (a re-suspend writes the step's `nextPollAt`, not-ready writes `now + pollInterval`, completed/failed/cancelled write `null`, a skipped claim outcome hands the stage back to the next tick), so the lease value only survives a process that dies mid-replay — that stage is picked up again once the lease elapses. The in-memory persistence behaves the same, so `createTestHarness` and a real deployment agree. No schema change: the claim uses the `version` column `updateStage` already guards on.
  - A claim outcome that finds the run no longer `RUNNING` marks the stage `CANCELLED` only when the run is `CANCELLED`. A run that is `COMPLETED`, `FAILED` or gone was finished by another orchestrator (its lease elapsed while this one was still replaying); the stage row already carries that outcome and is left alone — two runs had ended with a `CANCELLED` stage under a `COMPLETED` run.
  - `@bratsos/workflow-engine-host-node` 0.4.3: an orchestration interval firing while a tick is still in flight is skipped, not queued (a replay longer than `orchestrationIntervalMs` no longer overlaps the next tick in the same process), `orchestrationTicks` counts only ticks that ran, and `stop()` waits for the in-flight tick (bounded by `shutdownTimeoutMs`) before the final outbox flush. The serverless host is caller-driven and unchanged.

  **Fixes from the fourth consumer round (1.0.0-alpha.3):**

  - OpenAI strict structured outputs (native, and through OpenRouter — seen on `openai/gpt-5-nano`, realtime and batch) also require every property to be listed in `required`, so an optional property still failed with `required is required to be supplied and to be an array including every key in properties`. The OpenAI rewrite now lists every property of every object in `required` and sends an optional, non-nullable property as `anyOf: [<original>, { type: "null" }]`, as OpenAI documents; a reply's `null` for such a property is then removed before validation — recursively through nested objects, arrays and union members, `$defs` followed — so the caller's Zod schema (`.optional()`) still parses (`stripOptionalNulls` in `schema-portability.ts`). A `null` the original schema admits (required or `.nullable()`) is kept. The middleware applies it to `generateObject`, `generateText` + `Output.object` and every `ctx.step.ai.*` call; the OpenAI and OpenRouter batch bodies carry the same schema and `getResults` strips before validating. Google and other targets are untouched. Verified live through OpenRouter → `openai/gpt-5-nano` with a discriminated union whose members have optional properties.
  - No default `temperature` is sent. GPT-5 endpoints reject `temperature: 0.7` under OpenRouter's `requireParameters`, and the alpha.1 unification (`generateObject` 0 → 0.7 to match `generateText`) had introduced a default no provider needs. `generateText`, `generateObject`, `streamText`, `ctx.step.ai.*`, `map` and both batch bodies carry `temperature` only when the caller sets it; the provider's own default applies otherwise. Set `temperature` explicitly where a fixed value was relied upon.
  - `run.transition` no longer copies the run's max stage `attempt` onto the next execution group: after a retried stage 1 (attempt 2) a stage 2 that had never executed read `attempt 2`. A stage's `attempt` counts the executions of its own row — job retries and `run.rerunFrom` reruns — so a fresh downstream stage starts at 0 (the `prepareExecutionGroup` `"max"` mode is gone). Consequence for annotations: after a rerun, a recreated downstream stage's annotations carry attempt 0 again; only the rerun target's row is bumped.
  - A `ctx.step.ai.map` batch item bound for the repair pass was listed in the `${id}:collect` summary under both `failed` (with its batch tokens and cost) and `repair` (with the same as its prior attempt), so its batch cost counted twice. Each item is now listed once: under `repair` when it will be re-prompted (the item's verdict then continues from that prior — batch cost plus the repair call), under `failed` only when the batch verdict is final (`repair.attempts: 0`).

  **Fixes from the third consumer round (1.0.0-alpha.2):**

  - `WorkflowStage.attempt` is persisted: `UpdateStageInput.attempt` exists and the Prisma adapter writes it, so a stage row counts its job retries (it stayed at 0 through three attempts while `version` advanced; the in-memory adapter already merged it).
  - A retried stage that completes through a suspension — the batch poll/collect resume, a `waitFor`, a `checkCompletion` — clears its stale `errorMessage` like a direct completion does.
  - Ledger rows keep their attempt history: a `run` step or map item re-opened for a new job attempt goes back to `running` with no lease and keeps its `attempt` (a row that read `failed attempt 3` re-runs as attempt 4) instead of being reset to 0; in-process map retries increment the row's attempt rather than assigning it.
  - `outbox.flush` claims rows before it emits them: `WorkflowPersistence.claimUnpublishedOutboxEvents(limit)` stamps `publishedAt` atomically (`UPDATE ... FROM (SELECT ... FOR UPDATE SKIP LOCKED) RETURNING` on Postgres, a per-row compare-and-set on SQLite and in memory) and `releaseOutboxEvents(ids)` hands back the events of a run whose emit threw. Two hosts flushing the same outbox — a cron tick and a request-kicked tick — no longer both deliver `workflow:created`. Both methods are required on a custom `WorkflowPersistence`; the conformance suite covers them.
  - OpenRouter batch status/results schemas accept `null` for every field an upstream may null (`results[].response.request_id` came back `null` from deepseek via Together, and the poll looped on "invalid batch object" until the deadline).
  - The first three consecutive failures of a `waitFor` poll are logged at DEBUG and the streak escalates to WARN from the fourth (OpenRouter answers 404 to the first status check after a submit); the count is stored on the row (`waitState.pollFailures`) and reset by a poll that returns.
  - The missing-vendor-SDK fallback to OpenRouter no longer requires a catalog `batchModelId`: a batch-capable entry without one assumes the `<id>:batch` row (as the sync CLI derives it), and the WARN says to regenerate the catalog; a row that is not live fails the submit with OpenRouter's "does not have a :batch endpoint" as before.
  - A clean batch no longer stores every verdict in the `${id}:collect` step result (92 KB for 27 items): the collect row holds counts, the failed items and the repair feedback, and each item's verdict lives on its own `${id}:${itemId}` row, completed or failed, as on the realtime path. A replay that finds an item row missing (the process died between the collect and that row) re-fetches the batch results; the logger records accounting once per batch id.
  - Structured-output schemas are made portable per target. OpenAI's strict structured outputs (native, and through OpenRouter's chat and `:batch` endpoints) reject the `oneOf` that `z.discriminatedUnion` emits, and Gemini drops it; every JSON `responseFormat` sent to an OpenAI, OpenRouter or Google model is rewritten at the model boundary (`oneOf` → `anyOf`, `additionalProperties: false` for OpenAI, `$schema` stripped) through an AI SDK middleware, so `generateObject`, `generateText` + `Output.object`, `streamText`, every `ctx.step.ai.*` call and the OpenAI/OpenRouter batch bodies all send a schema the target accepts while validation stays on the original Zod schema. Verified live on Google (`gemini-2.5-flash-lite`) and OpenRouter (`openai/gpt-5-nano`, Azure-OpenAI upstream) with a nested discriminated union; the raw provider path still fails with `'oneOf' is not permitted`.

  **Fixes from the second consumer round (1.0.0-alpha.1):**

  - Google batches send a `responseSchema` the batch endpoint enforces and that keeps unions. Probed live: Gemini's `batchGenerateContent` ignores `generationConfig.responseJsonSchema` for a small schema and rejects it per request (`code 3 "Request contains an invalid argument"`) for a real one, so alpha.1's fix answered nothing; the provider's own OpenAPI conversion forwards `oneOf` (which Gemini's `Schema` lacks) and drops array bounds, which is why alpha.0 flattened discriminated unions. The engine now converts the JSON Schema itself — `oneOf`/`anyOf` to `anyOf`, `const` to `enum`, `null` branches to `nullable`, `$defs` inlined, bounds kept — and substitutes it at the fetch boundary as before. Verified live against a 7 KB schema with nested discriminated unions: the batch reply validates against the original schema.
  - Batch failure visibility: the poll logs a WARN when a settled batch reports failed requests, and the "more than half failed" WARN covers provider-side failures as well as schema validation, naming the class and the first error. Batch accounting rows store the model's reply — its raw text when it failed validation — and `metadata.batchDurationMs` (the batch wall time) instead of repeating it as a per-row `durationMs`.
  - A batch is polled and collected through the transport its stored refs name, not whatever the registry resolves for the model key at poll time; changing `batchProvider` while a batch is in flight no longer strands the run with "belongs to unknown provider".
  - Vendor resolution reads `ModelConfig.provider`: a `provider: "google"` entry is the Google vendor whether its `id` is the bare model id or the catalog slug, and the batch and realtime paths both strip the vendor prefix — one entry serves `map` batches and their realtime repair (the slug 404ed on the Google API before). The missing-vendor-SDK fallback to OpenRouter also engages on workerd, whose dynamic-import error is `No such module "@ai-sdk/openai".` without a code.
  - A failed step is re-executed on the next job attempt: a retry of a stage whose last attempt threw re-opens every `run` step and every `map` item that ended `failed` (their ledger rows keep the failure but are re-claimed), so a `${id}:submit` that hit a 503 or an item that exhausted its repair budget gets a fresh call instead of replaying the stored failure; completed steps still replay, and a poll of the same attempt still answers failures from the ledger. Map verdicts are stored on the item's `failed` row itself (no more `${id}:${itemId}:failed` memo step). `WorkflowStage.attempt` now counts job retries too (0 on the first execution).
  - `stage:retrying` (`attempt`, `maxAttempts`, `error`) is emitted for a retried attempt; `stage:failed` is emitted only when the stage row becomes `FAILED`.
  - Host job results carry the retry contract: `executeJobWithHeartbeat` and the serverless host's `handleJob` return `willRetry`, `attempt`, `maxAttempts` and `retryDelayMs` (the built-in transports' `2^attempt` seconds), so a push transport whose `fail()` cannot re-enqueue (a Cloudflare Queue consumer) retries the message itself; the README states the contract. Malformed job messages (no `payload`, no `workflowId`) are validated up front and failed as dead jobs (`dead: true`) instead of throwing from inside `job.execute`.
  - A stage that fails terminally from the poll path (a step retry that ran inside `stage.pollSuspended`, a `checkCompletion` error, a wait past its deadline) finalises its `job_queue` row (`FAILED`, `completedAt`) instead of leaving it `SUSPENDED`.
  - A stage waiting on a leased in-flight step after a crash announces `stage:suspended` / `workflow:suspended` once, not on every 5s poll: the step id is the identity of the wait.
  - `PrismaWorkflowPersistence.withTransaction` re-applies every constructor option (`statusEnumName`, `now`, ...) to the transactional clone; `run.claimPending` inside a transaction no longer fails with `42704 type "Status" does not exist` on a schema that names the enum differently.
  - `PrismaJobQueue.dequeue` on Postgres fails a row whose `payload` is NULL as a dead job (logged with the job id) and takes the next row instead of throwing and aborting the tick.
  - Failed `generateObject`/`generateText` calls log the tokens (and cost) the thrown `NoObjectGeneratedError` carries instead of 0/0, and `WorkflowRun.totalCost`/`totalTokens` are rolled up on `FAILED` runs as well as `COMPLETED` ones.
  - `workflow-engine-codemod` runs when invoked through a symlinked bin (`npx`, `pnpm exec`, a pnpm-linked `node_modules` path): the "am I the entry point" guard compares real paths.
  - `workflow-engine-sync` output is 1.0-clean: it emits absolute batch prices (the native vendor discount applied to the model's own prices when the catalog has no `:batch` sibling) instead of `batchDiscountPercent`, the field codemod rule 7 flags, and stamps `batchProvider: "openrouter"` on models only OpenRouter can batch.
  - Reference: step results are small JSON (large payloads go to the blob store or artifacts, the step returns the key); the retry semantics above are documented in 12-durable-steps.md, 08-common-patterns.md and the 0.13 → 1.0 migration guide.
